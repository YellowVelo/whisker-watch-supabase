## Current data model — read before touching scoring/check-in logic
`/docs/features/0012_DailyCheckIn_Vibe_Trends_Specification_v5.md` is the canonical source for all Vibe/scoring/check-in logic. This model is stable and settled — the prior iterations (Wellness Score V1, Health Score V2, an equal-weight multi-select version) are retired history, not an ongoing concern. If any other file, doc, or piece of code appears to reference a 0–100 score, a 0–10 Health Score, or Stable/Declining/Monitor labels, treat it as outdated and check this spec first.

Current model in one line: `daily_check_ins.status` is `great` / `off` / `tough` / `skipped` (Vibe, subjective, owner-reported) plus an unweighted symptom count (objective, direction-only). The two signals never inform each other.

## Key architecture
- **`supabase/migrations/0052_restore_storage_policies.sql`** — restores production's `storage.objects` RLS policies (the 4 rules from `0002_storage_bucket.sql`: public read, insert/update/delete own-folder-only). **Found 2026-08-30 (spec 0063):** production's migration history claimed `0002` had run, but a direct query (`select policyname, cmd, qual, with_check from pg_policies where schemaname='storage' and tablename='objects'`) showed zero policies actually existed there — something outside the migration system (most likely a manual dashboard change or a pre-`0002` backup restore) had silently dropped them, with nothing in CI or the deploy process to catch it. **Migration history alone is not proof an environment's actual DB state matches another's** — check here before trusting that a migration "ran successfully" means its effects still exist, especially for any prod-vs-dev/staging discrepancy. No automated cross-environment policy-diff tooling exists yet (flagged as a future follow-up in spec 0063, not built).
- `src/components/ui/{toast,toaster,use-toast}.jsx` — the app's one toast/notification system, used everywhere (error messages, confirmations, etc.). **Fixed 2026-08-29**: since the app's very first commit (2026-06-21), `toast.jsx` stubbed out `ToastProvider`/`Toast`/`ToastClose`/etc. as plain `<div>`s/a Fragment instead of the real `@radix-ui/react-toast` primitives (already installed in `package.json`, just never wired up) — meaning every toast the app had ever shown rendered in normal page flow (`position: relative`, wherever `<Toaster/>` happened to sit in the DOM) instead of pinned to the screen (`position: fixed`), so toasts were silently landing hundreds of pixels below the fold. This had nothing to do with the z-index stacking scale (spec 0059) — z-index only affects paint order between positioned elements, and these were never positioned at all. Now genuinely wired to Radix. Also fixed in the same pass: `TOAST_REMOVE_DELAY` was `1000000` (~16.6 minutes, a shadcn/ui template artifact) — now `5000`. Check here before assuming a toast-not-appearing bug is a z-index/stacking issue — verify the toast is even reaching `position: fixed` first. Also: AI/scan failures in `VaccinationSection.jsx` now report to Sentry (`Sentry.captureException`) in addition to showing a toast — previously a failure there had no record anywhere except a toast, an app-wide pattern for AI-calling catch blocks worth checking before assuming a new one already has it. See `0062_Toast_System_Position_Fix_Specification_v1.md` for the full investigation.

Check here before writing a new AI-facing prompt, disclaimer, or error message — 3 near-duplicate disclaimer copies existed before 2026-08-02, and 5 call sites had no error handling at all before 2026-08-09.

- `src/components/VaccinationSection.jsx` (AI-powered "Scan Record" upload) + `src/components/ScanReviewSheet.jsx` — scanning a vaccine document (e.g. a vet invoice) never saves immediately (spec 0061): it opens a review step first, grouped by pet, where every field is editable and each line can be individually excluded before a single confirm writes anything. A scanned line is attributed to a pet by matching a `pet_name` the AI returns against the account's real pets (`entities.Pet.list()`); anything unmatched defaults to the pet whose page the scan was launched from, never guessed onto a different pet. Medications are deliberately out of scope — the AI prompt only asks for vaccinations, and anything else in the document is ignored entirely, never surfaced or saved. **Fixed 2026-08-30 (spec 0064):** the existing-record match used for "Will update" vs "New" was a plain exact-string comparison, so a real scanned invoice returning wording like "Canine - Rabies Vaccine" never matched a stored "Rabies Vaccine" record and created duplicates. `src/lib/speciesConfig.js`'s `vaccineNamesMatch(nameA, nameB, species)` now anchors matching to the same known-vaccine list used for the Add/Edit form's suggestion chips (`DOG_VACCINES`/`CAT_VACCINES`) — two names both resolving to the same canonical vaccine count as a match regardless of wording, and anything not on that list still falls back to exact match, deliberately, to avoid guessing at unfamiliar names. Check here before changing Scan Record's save behavior or building a second document-scanning entry point elsewhere.

## Working conventions
- **Claude Code is the developer (hard rule, 2026-11-07).** All Wysker Watch development — code, diagnosis, review — is done by Claude Code. Never hand work to Codex or ChatGPT (no `codex:rescue` agent, no `codex:*` skills), even when stuck; keep working or ask Lynn. Codex may stay installed on Lynn's machine but doesn't work on this repo. If `AGENTS.md` or `.agents/` reappears (Codex auto-generated them once from imported Claude transcripts), flag it to Lynn instead of committing it.
- **One branch at a time (hard rule, 2026-11-07).** Only one working branch besides `main`/`staging`/`dev` may exist at any time. Before creating a branch, worktree, or side session that writes code, check `git branch -a` and `gh pr list`: if another working branch is unmerged, finish it (merge its PR, or close it with Lynn's OK) or add the new work to that same branch instead. Side sessions that write code use the current branch (`use_worktree: false`), never a new worktree. After a PR merges, delete its branch (local + remote) and its worktree in the same turn. Why: on 2026-11-07 Lynn came back to 13 local branches and 3 worktrees, with the only real unmerged work buried in one of them, and couldn't tell what to do first.
- **User-facing copy needs Lynn's review before it goes to CC.** Any marketing/page copy Claude drafts as part of a feature (hero text, CTAs, confirmation messages, anything a real visitor reads) gets shown to Lynn for approval before the spec/build is handed off to CC for deploy — not bundled silently into the implementation. Gap found 2026-08-15: the Early Adopters page (spec 0056) shipped to CC with placeholder hero copy Lynn hadn't reviewed, and needed a brand-voice rewrite after the fact. Catch this before handoff going forward, not after.
- **Brand voice (compassionate, not scary; sarcastic, not cruel).** Per Lynn's brand guidelines (2026-08-15): Wysker Watch doesn't scare people, and it's compassionate first. Social/marketing copy's sarcasm is aimed at the owner's own anxious habits (2am Googling, treating a cough as a diagnosis, photographing poop like evidence) — never at the pet's actual health, medical uncertainty, grief, or the owner's competence. This is the same spirit already documented in the `Voice & Legend` tab of `social/Wysker_Watch_2026_Social_Media_Calendar.xlsx` for social posts; it applies to any Wysker Watch-authored copy, in-app or on social, not just scheduled posts.
