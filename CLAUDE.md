## Current data model — read before touching scoring/check-in logic
`/docs/features/0012_DailyCheckIn_Vibe_Trends_Specification_v5.md` is the canonical source for all Vibe/scoring/check-in logic. This model is stable and settled — the prior iterations (Wellness Score V1, Health Score V2, an equal-weight multi-select version) are retired history, not an ongoing concern. If any other file, doc, or piece of code appears to reference a 0–100 score, a 0–10 Health Score, or Stable/Declining/Monitor labels, treat it as outdated and check this spec first.

Current model in one line: `daily_check_ins.status` is `great` / `off` / `tough` / `skipped` (Vibe, subjective, owner-reported) plus an unweighted symptom count (objective, direction-only). The two signals never inform each other.

## Key architecture
- **`supabase/migrations/0052_restore_storage_policies.sql`** — restores production's `storage.objects` RLS policies (the 4 rules from `0002_storage_bucket.sql`: public read, insert/update/delete own-folder-only). **Found 2026-08-30 (spec 0063):** production's migration history claimed `0002` had run, but a direct query (`select policyname, cmd, qual, with_check from pg_policies where schemaname='storage' and tablename='objects'`) showed zero policies actually existed there — something outside the migration system (most likely a manual dashboard change or a pre-`0002` backup restore) had silently dropped them, with nothing in CI or the deploy process to catch it. **Migration history alone is not proof an environment's actual DB state matches another's** — check here before trusting that a migration "ran successfully" means its effects still exist, especially for any prod-vs-dev/staging discrepancy. No automated cross-environment policy-diff tooling exists yet (flagged as a future follow-up in spec 0063, not built). **Superseded by spec 0071 (PA-01):** 0052's restored public-read rule was itself the hole (anyone, even logged out, could list and download every pet photo and vet document). `0054` adds the replacement rule `uploads_read_permitted`; `0055` makes the bucket private and drops `uploads_public_read`. `0055` refuses to run on an environment until `private.deploy_markers` has `spec_0071_frontend_live` (snippet in its header), so a `db push` can't lock the bucket before that environment's frontend is live. **Migration 0061 (spec 0081)** drops `symptom_logs`, `wellness_scores` and `food_logs` and adds spreadsheet types to the bucket. Its gate marker is `spec_0081_frontend_live`. Order on each project: frontend promoted → marker → functions deployed → `db push --include-all` (0062 ran first). The old functions read the dropped tables, so the functions must go before the push. `scripts/restore-test.sh` sets both markers and skips the dropped tables' data.
- `src/components/ui/{toast,toaster,use-toast}.jsx` — the app's one toast/notification system, used everywhere (error messages, confirmations, etc.). **Fixed 2026-08-29**: since the app's very first commit (2026-06-21), `toast.jsx` stubbed out `ToastProvider`/`Toast`/`ToastClose`/etc. as plain `<div>`s/a Fragment instead of the real `@radix-ui/react-toast` primitives (already installed in `package.json`, just never wired up) — meaning every toast the app had ever shown rendered in normal page flow (`position: relative`, wherever `<Toaster/>` happened to sit in the DOM) instead of pinned to the screen (`position: fixed`), so toasts were silently landing hundreds of pixels below the fold. This had nothing to do with the z-index stacking scale (spec 0059) — z-index only affects paint order between positioned elements, and these were never positioned at all. Now genuinely wired to Radix. Also fixed in the same pass: `TOAST_REMOVE_DELAY` was `1000000` (~16.6 minutes, a shadcn/ui template artifact) — now `5000`. Check here before assuming a toast-not-appearing bug is a z-index/stacking issue — verify the toast is even reaching `position: fixed` first. Also: AI/scan failures in `VaccinationSection.jsx` now report to Sentry (`Sentry.captureException`) in addition to showing a toast — previously a failure there had no record anywhere except a toast, an app-wide pattern for AI-calling catch blocks worth checking before assuming a new one already has it. See `0062_Toast_System_Position_Fix_Specification_v1.md` for the full investigation.

- `src/lib/errorMonitoring.js` (client) + `supabase/functions/_shared/errorReporting.ts` (Edge Functions) — shared Sentry error/crash monitoring (spec 0052). **`@sentry/deno` is pinned to 11.15.0 (2026-11-21, spec 0075).** 11.16.0 hands `Deno.unrefTimer` a Node timer object, which Supabase's runtime (Deno 2.1.4) rejects, so every function crashes on startup with `WORKER_ERROR`. That broke `sign-up` on staging and prod from 01:11 to 23:12 UTC, and no test noticed. A local test won't catch this, because current Deno accepts the object. Before raising the version, deploy a test function to dev and call it once. PA-34's flush didn't need an upgrade (spec 0078): `reportError()` now gives every report up to 2s to finish sending, via `EdgeRuntime.waitUntil(Sentry.flush(2000))`, without delaying the reply. Every `npm:`/`jsr:` import names an exact version (spec 0078), enforced in CI by `supabase/tests/function_hygiene.test.ts`. After any function deploy, run `scripts/check-functions-start.sh <project-url>` (`0006 Technical Standards.md` §11). `.github/workflows/function-health.yml` also runs it hourly on all 3 projects (URLs in the GitHub Actions variables `DEV_/STAGING_/PROD_SUPABASE_URL`). **Spec 0078 helpers:** in Edge Functions, a top-level catch uses `serverError(err, tags, cors)`, which reports to Sentry and answers 500 with the plain "Something went wrong. Please try again." It never sends a raw `err.message` to the browser (`send-email` is the one exception: it's ops-only). In the app, use `reportClientError(err, { feature, note })` instead of `console.error` (a unit test fails on any `console.error` left in `src/`). Read a failed function call's reason with `functionErrorMessage(error, data, fallback)`, never `error.message`, which is supabase-js's own "Edge Function returned a non-2xx status code". Both no-op silently if no DSN is configured (`VITE_SENTRY_DSN`/`SENTRY_DSN`). The client (`errorMonitoring.js`, `shouldSendEvent`) drops only `test` and `demo` events; `production`, `owner` (Lynn's own account, since spec 0078) and not-yet-signed-in errors are sent. The Edge Function helper does **not** filter, so test-account backend errors do reach Sentry. Backend live-fire confirmed on all 3 projects 2026-10-23 (spec 0066) — check here before adding a new error-reporting call site or a second monitoring mechanism. **Investigated 2026-09-01 (spec 0065):** a suspected "production has never sent a single Sentry event" bug turned out to be a false alarm — live testing confirmed events reach Sentry correctly in both production and local dev. The only real bug found: a local `.env` file (gitignored) can have a duplicate `VITE_SENTRY_*` key block further down the file silently override an earlier correct one, with no error or warning — worth a quick visual scan of `.env` for accidental duplicates if a similar mistagging issue ever resurfaces. Also worth knowing: this repo's own network-request-logging tooling failed to show a request that demonstrably succeeded (confirmed via the browser's Performance Resource Timing API and the Sentry dashboard itself) — don't treat "the Network tab shows nothing" as proof a request never happened without corroborating another way.
