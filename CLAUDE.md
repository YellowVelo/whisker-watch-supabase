## Current data model — read before touching scoring/check-in logic
`/docs/features/0012_DailyCheckIn_Vibe_Trends_Specification_v5.md` is the canonical source for all Vibe/scoring/check-in logic. This model is stable and settled — the prior iterations (Wellness Score V1, Health Score V2, an equal-weight multi-select version) are retired history, not an ongoing concern. If any other file, doc, or piece of code appears to reference a 0–100 score, a 0–10 Health Score, or Stable/Declining/Monitor labels, treat it as outdated and check this spec first.

Current model in one line: `daily_check_ins.status` is `great` / `off` / `tough` / `skipped` (Vibe, subjective, owner-reported) plus an unweighted symptom count (objective, direction-only). The two signals never inform each other.

## Key architecture
- `src/api/entities.js` — entity CRUD
- `src/api/storageClient.js` — file uploads
- `src/api/aiClient.js` + `supabase/functions/ask-vet-assistant` — AI features via Anthropic API through a Supabase Edge Function. The Edge Function caps each authenticated user at 20 requests per 10 minutes (spec 0050, reusing the `check_and_record_rate_limit` mechanism from migration 0039) — check here before assuming a new AI-calling feature needs its own rate limit built from scratch.
- `src/pages/BetaSignup.jsx` (public, no login) + `src/pages/admin/BetaSignups.jsx` (admin-only) + `supabase/functions/beta-signup` — the public beta-signup landing page and screener (spec 0053). `src/components/AdminRoute.jsx` is the app's **first** admin-gated route (checks `profiles.role === 'admin'`) — check here before hand-rolling another admin-only page. The Edge Function is also the app's **first** CAPTCHA (Cloudflare Turnstile, `VITE_TURNSTILE_SITE_KEY` / `TURNSTILE_SECRET_KEY`) and reuses `check_and_record_rate_limits` (migration 0039) the same way `sign-up`/`ask-vet-assistant` do. `beta_signups` is the first table with an admin-gated RLS policy, not just service-role-only.
- `src/pages/EarlyAdopters.jsx` (public, no login) + `supabase/functions/early-adopter-signup` — the public Early Adopters welcome page (spec 0056), a **pre-PWA-launch** "tell me when it's ready" signup for general social traffic, not testers. Structurally mirrors `/beta`'s Turnstile + `check_and_record_rate_limits` pattern, but writes to its own `early_adopters` table (no admin review UI, by design) — kept deliberately separate from `beta_signups` so the two audiences never mix. Not to be confused with the "Watch List," a distinct, later, not-yet-built pre-App-Store-phase list (Launch Plan task 65).
- `src/lib/aiGuardrails.js` — shared AI safety guardrails (spec 0041): emergency-keyword hard-stop, the `urgent`-flag backstop, and the disclaimer text every AI-facing prompt must use. Also (spec 0050) `aiErrorText()`, the shared copy for when an AI call fails (rate-limited or otherwise) — paired with `AIErrorNotice.jsx` for chat-style UI and a destructive toast for one-shot scan actions. Check here before writing a new AI-facing prompt, disclaimer, or error message — 3 near-duplicate disclaimer copies existed before 2026-08-02, and 5 call sites had no error handling at all before 2026-08-09.
- `src/lib/checkin/{scoring,config,chipLabels,checkinClient}.js` — current Vibe/symptom-count logic. `checkinClient.js`'s `markGreatDay`/`markOffTough` support opt-in co-owner conflict detection (spec 0043, migration 0046) via an `expectedUpdatedAt` param — check here before adding a new single-day check-in save path so it doesn't silently skip this.
- `src/components/catchup/` (`CatchUpFlow.jsx`, `BulkApplySheet.jsx`) — multi-day Catch-Up Check-In UI (2+ missed days), see `0015_MultiDay_CatchUp_CheckIn_Specification_v1.md`. The single-day "catch up yesterday" flow still lives in `DailyCheckInSheet.jsx`/`DailyCheckInModal.jsx`, unchanged.
- `src/components/{BottomSheet,ConfirmDeleteDialog,IconButton,ListRow,PillToggle}.jsx` — shared primitives from spec 0025's de-duplication pass. Check here before hand-rolling a new bottom sheet/pill-toggle/back-button/delete-confirmation/nav-row — 5+ separate copies of these existed before 2026-07-31.
- `src/components/ui/accordion.jsx` — shared expand/collapse accordion (spec 0051), themed to Design System tokens and used by the Support page's FAQ. Check here before hand-rolling a new expand/collapse pattern.
- `src/hooks/useFocusTrap.js` — shared keyboard focus-trap + Escape-to-close hook (spec 0045), used by `BottomSheet.jsx` and the full-screen overlays `CatchUpFlow.jsx`/`OnboardingShell.jsx`. Check here before adding a new modal/full-screen overlay so it doesn't silently ship without a focus trap the way `CatchUpFlow`/`OnboardingShell` originally did.
- `src/lib/pendingOAuthConsent.js` — sessionStorage handoff for state that needs to survive a Google OAuth full-page redirect (spec 0047: the signup-consent checkbox answer, read back by `AuthContext.jsx` once a fresh session exists). Check here before adding new state that needs to persist across an OAuth redirect, rather than inventing a new one-off sessionStorage key.
- `e2e/` — Playwright E2E suite (`npm run test:e2e`), always targets `wysker-watch-dev` via `.env.playwright` (gitignored; see `.env.playwright.example`). See `0024_Playwright_E2E_Testing_Specification_v1.md`. Also runs in CI as a non-blocking trial (spec 0055, through 2026-09-03) via a dedicated `e2e` job in `.github/workflows/ci.yml`.
- `e2e/fixtures.js` — shared Playwright test helpers (`dismissAnyOpenSheet`, `waitForOnboardingStep`). Check here before hand-rolling a new step-transition wait or sheet-dismissal pattern in a new e2e spec — the same "Step N of 6" wait was silently duplicated across 3 spec files before spec 0046 consolidated it. `test3@wyskerwatch.com` (migration `0049`) is a dedicated `profiles.role='admin'` fixture account for admin-route tests — kept separate from `test1@` (the suite's shared default session) and `test2@` (reserved for the Deno CI suite) so making one account admin never changes what "logged in" means for the rest of the suite. `test4@wyskerwatch.com` (migration `0051`) is a dedicated sitter-identity fixture account for `e2e/pet-sitter.spec.js`'s sitter-wellbeing-badge tests (spec 0057) — deliberately **not** wired into `fixtures.js`/`global-setup.js` like the other three; its sign-in and cleanup live entirely inside that one spec file, so no other spec is affected by it.
- Deployed on Cloudflare Workers (`wrangler.jsonc`). Deploy pipeline: push to the tracked branch → Cloudflare's git-integration build → Lynn manually promotes the build to production in the Cloudflare dashboard — push alone does not deploy. `npm run deploy` (`wrangler deploy`) exists locally but is a separate command, not part of this shipped pipeline. **Frontend deploys are done manually by Lynn, not Claude.** **Staging is a separate Cloudflare project (`wysker-watch-staging`), tracking the `staging` git branch, and auto-promotes with no manual gate** — confirmed 2026-08-11 after discovering staging had silently drifted ~150 commits behind main. Staging is synced to main only when Lynn explicitly asks (`git push origin main:staging`, safe as long as staging has no commits of its own — check `git log origin/main..origin/staging` first if that's ever in doubt). **Cloudflare plan is Free tier, not Pro/Business** (confirmed 2026-08-13, spec `0054`) — this caps what's configurable (e.g. WAF rate-limiting rules have a fixed 10-second window on Free, can't be widened) — check here before scoping new Cloudflare-side security/traffic rules. **Bot Fight Mode is on** for the zone (covers both `whisker-watch-supabase` prod and `wysker-watch-staging`, since it's zone-wide, not per-project); the app has no other Cloudflare-level traffic/bot rules beyond that — see `0054_Cloudflare_Traffic_And_Bot_Protection_Runbook_v1.md`.
- Three separate Supabase projects exist for the app itself: `Whisker-Watch` (prod), `wysker-watch-dev` (local dev), `wysker-watch-staging`. Local `.env` points at `wysker-watch-dev` — confirmed 2026-07-21, see `.env.example`. This corrects an earlier, stale version of this file that claimed local dev and prod shared one project. **Backend changes (migrations, Edge Functions) should be pushed to all three projects as part of shipping — this is manual, not automated, and has been missed before (see `0006 Technical Standards.md` §11).** A 4th Supabase project, `wysker-watch-restore-scratch`, also exists but is not part of the app's deploy targets — it's a disposable scratch database the quarterly automated restore drill wipes and rebuilds every run (spec `0048`); never push migrations or app data to it.
- CI (`.github/workflows/ci.yml`) runs lint/typecheck/vitest/build + Edge Function integration tests, required on `main` via branch protection as of 2026-07-24 — note: this gates PR merges; an account with bypass permission can still push directly without CI blocking it (tracked in the launch planner, see below). `typecheck` was added 2026-08-04 (spec `0044`) after clearing 308 pre-existing errors — see `0006 Technical Standards.md` for the frontend's `checkJs`-based approach. A third job, `e2e` (spec 0055), also runs the Playwright suite on every PR/push but is currently non-blocking (`continue-on-error`) during a 3-week trial period through 2026-09-03, pending no false-positive failures from a known unresolved flake in `login.spec.js` (spec 0046).
- **Backups:** Nightly `pg_dump` → R2 (`db-backup.yml`, spec pre-0048) covers the database. A separate nightly job, `storage-backup.yml` (spec `0049`), syncs the `uploads` Supabase Storage bucket (pet photos, document scans) into a *different* dedicated R2 bucket (`whisker-watch-storage-backups`) — additive-only, production only. Check `docs/features/requirements-database-backups.md` before assuming either backup covers something it doesn't; the two are separate systems with separate credentials.
- `src/lib/errorMonitoring.js` (client) + `supabase/functions/_shared/errorReporting.ts` (Edge Functions) — shared Sentry error/crash monitoring (spec 0052). Both no-op silently if no DSN is configured (`VITE_SENTRY_DSN`/`SENTRY_DSN`) and both drop/tag events by `account_type` so sandbox/test accounts never pollute production error signal — check here before adding a new error-reporting call site or a second monitoring mechanism.

## Working conventions
- **User-facing copy needs Lynn's review before it goes to CC.** Any marketing/page copy Claude drafts as part of a feature (hero text, CTAs, confirmation messages, anything a real visitor reads) gets shown to Lynn for approval before the spec/build is handed off to CC for deploy — not bundled silently into the implementation. Gap found 2026-08-15: the Early Adopters page (spec 0056) shipped to CC with placeholder hero copy Lynn hadn't reviewed, and needed a brand-voice rewrite after the fact. Catch this before handoff going forward, not after.
- **Brand voice (compassionate, not scary; sarcastic, not cruel).** Per Lynn's brand guidelines (2026-08-15): Wysker Watch doesn't scare people, and it's compassionate first. Social/marketing copy's sarcasm is aimed at the owner's own anxious habits (2am Googling, treating a cough as a diagnosis, photographing poop like evidence) — never at the pet's actual health, medical uncertainty, grief, or the owner's competence. This is the same spirit already documented in the `Voice & Legend` tab of `social/Wysker_Watch_2026_Social_Media_Calendar.xlsx` for social posts; it applies to any Wysker Watch-authored copy, in-app or on social, not just scheduled posts.
