## Before You Approve This

- **This moves account creation out of the browser and into new server-side Edge Functions — two, not one, as of this revision.** Today, `Register.jsx` creates the account itself by calling Supabase directly (`supabase.auth.signUp()`). This spec now involves: one function handling both signup and resend (branching on `action`), plus a small second, authenticated `confirm-email` function that `VerifyEmail.jsx` calls after redeeming the token, added specifically so email confirmation doesn't depend on unverified assumptions about `recovery`-type token behavior (see Technical Spec). **Note:** hosted Supabase also supports branding its *own* default confirmation email via dashboard-configured templates, without moving account creation server-side at all — that alternative was considered and rejected earlier in this process because it would need to be configured identically by hand across all three Supabase projects with no version-controlled record of the config, whereas this approach lives in code like the rest of the app's email system. Flagging again here since it's a real fork, not a formality.
- **This is a genuinely public, unauthenticated endpoint** (there's no logged-in user yet — that's the whole point of signup), unlike `invite-co-owner`, which only a signed-in user can call. That changes the security bar significantly: input validation, rate limiting, and safe error responses all need to be real requirements here, not implied by copying the invite pattern. This revision adds those as explicit requirements below.
- **A second template (`welcome`) was found to be dead code during this investigation, same as `verify-email` was.** Not part of this spec's scope, flagged so it isn't lost.
- **This spec grew slightly beyond "just brand the email"** at your direction: it also adds a "resend confirmation email" option on the Login screen. That's new UI, not just new email copy — flagged so the scope increase is visible.
- No conflicts with CLAUDE.md's locked decisions (Vibe/scoring model) — this is unrelated, purely auth/email infrastructure.
- **Live Supabase Auth dashboard settings for all three projects (prod/dev/staging) were not inspected as part of this spec** — only repo code and migrations were. If any project has non-default Auth settings (e.g. email confirmations disabled, a custom SMTP already configured), that needs to be checked before implementation, not assumed from the code alone.

## Functional Requirements

1. When someone creates a new Wysker Watch account with an email and password, the confirmation email they receive must look like every other Wysker Watch email (same dark branded layout, same "Wysker Watch" name and styling) — not Supabase's generic default confirmation email.
2. Clicking the confirmation link in that email must confirm the account and sign the person straight into the app, exactly as it does today — no extra "set a password" step, since they already chose one during signup.
3. If someone doesn't confirm right away and later tries to log in, they should have a way to get a new confirmation email sent to them, instead of being stuck with no path forward except contacting support.
4. Signing up with Google ("Continue with Google") is unaffected — Google-verified accounts never went through Supabase's confirmation email and won't go through this new one either.
5. **(New)** Because this endpoint is reachable by anyone on the internet (not just logged-in users), it must not become a way to spam arbitrary email addresses, rack up Resend costs, or reveal whether a given email address already has an account.

## Acceptance Criteria

- **Given** a new user fills out the signup form with a real email and password, **when** they submit, **then** they receive an email from Wysker Watch's branded template (dark background, "Wysker Watch" header, styled button) containing a "Verify email" call-to-action — not Supabase's plain default template.
- **Given** a user clicks the "Verify email" button in that email, **when** the link is valid and unused, **then** they land back in the app already signed in, the same way confirming email works today (redirect target: `/`, matching current post-confirmation behavior — no new onboarding-vs-home branching introduced by this spec).
- **Given** a user clicks an expired or already-used confirmation link, **when** the page loads, **then** they see a clear "this link is invalid or has expired" message — **unless** a session already exists from an earlier successful redemption of the same link (e.g. an email client's link-preview scanner opened it first), in which case they're treated as verified, mirroring `AcceptInvite.jsx`'s existing fallback-to-session-check logic exactly.
- **Given** a user who signed up but never confirmed tries to log in, **when** the login attempt fails specifically because the email isn't confirmed (detected via the Supabase error's `code` field, e.g. `email_not_confirmed`, with a message-substring fallback only if the installed `supabase-js` version doesn't expose `code` — confirm at implementation time), **then** they're shown an option to resend the confirmation email.
- **Given** a user clicks "resend confirmation email," **when** the request succeeds, **then** a new branded email is sent to the same address, and the button becomes disabled/shows a cooldown (e.g. 60 seconds) to prevent rapid repeated sends to the same address from one browser session.
- **Given** someone submits the signup form (or the resend form) many times in a row for the same email address or from the same source, **when** a defined rate limit is exceeded, **then** further attempts are rejected without sending additional email, and the rejection response looks the same to the caller whether the address exists, doesn't exist, or is already confirmed (no account-existence enumeration via response shape or timing).
- **Given** a user signs up via "Continue with Google," **when** they complete Google's flow, **then** nothing about this change affects them — no confirmation email of any kind, same as today.
- **Given** the new user's email matches the existing test/demo allowlist (`test1@wyskerwatch.com`, `test2@wyskerwatch.com`, `demo1@wyskerwatch.com` — see migration `0010_account_type.sql`), **when** the confirmation or resend email would be sent, **then** it is suppressed the same way every other email already is, using the existing `sentByUserId` check in `sendEmail()` — **no new suppression logic needed**, because the `profiles` row (and its `account_type`) is created synchronously by the `handle_new_user()` trigger the moment the auth user is created, before `sendEmail()` is ever called (see Technical Spec below — this corrects the previous draft's incorrect assumption that no profile exists yet at send time).
- **Given** the auth account is created successfully but the branded email fails to send (Resend down, recipient suppressed, misconfiguration), **when** the signup request completes, **then** the account still exists (not rolled back) and the user can recover via the resend flow once the underlying problem clears — see Technical Spec's "Partial failure" note for why rollback is deliberately not attempted.

## Technical Spec

### Schema
- No new tables or columns. `email_logs` (existing) logs this the same way it logs every other template send.
- **Correction from the previous draft:** the new user's `profiles` row is **not** missing at send time. `handle_new_user()` (migration `0001_init_schema.sql`, extended by `0010_account_type.sql`) runs as an `after insert on auth.users` trigger, so the moment the Edge Function creates the auth user, a `profiles` row already exists with `account_type` correctly classified by email (production/test/demo). `related_entity_type`/`related_entity_id` on the `email_logs` row for this send should point at that `profiles` row (`related_entity_type: 'profiles'`, `related_entity_id: <new user id>`).

### API / Edge Functions

- **Decided: one Edge Function handles both signup and resend**, branching on an `action: 'signup' | 'resend'` field in the request body, rather than two separate functions — mirrors how `invite-co-owner` already handles its own two cases (first-invite vs. re-invite) in one function, and is one fewer function to deploy/monitor across three projects. Resolves former Open Question 4.
- **New Edge Function** (name TBD at implementation time, e.g. `sign-up`) — a **public, unauthenticated** endpoint (unlike `invite-co-owner`, which requires an existing session). Replaces the client's direct `supabase.auth.signUp()` call.
  - Accepts `{ email, password, first_name }` from `Register.jsx`.
  - **Server-side validation required** (client-side validation in `Register.jsx` is not sufficient for a public endpoint): re-validate email format, cap `first_name` length (mirror the existing 100-char `maxLength` already in `Register.jsx`), reject oversized request bodies.
  - **Decided: the Edge Function enforces its own password-length/complexity check explicitly, rather than trusting the Supabase admin account-creation call to apply whatever policy is configured on the project.** It's unconfirmed whether that privileged admin call enforces the same project-level password policy the public `signUp()` surface does, and today's `Register.jsx` has no client-side password rule at all to fall back on. Rather than depending on an unverified assumption either way, the function owns the check directly (minimum length at least; `Register.jsx` should mirror the same rule client-side for early feedback). Resolves former Open Question 7 — no further verification against live project settings needed for this to be safe.
  - **Rate limiting required**, keyed at minimum by recipient email and by request IP (implementation approach — e.g. a Postgres-backed counter table similar in spirit to `email_suppressions`, or an edge-level mechanism — left open, but the requirement itself is not optional; ungated, this endpoint can be used to spam arbitrary addresses or run up Resend costs). **Decided starting thresholds** (adjustable post-launch, err strict rather than loose): 5 signup/resend attempts per email address per hour, and 20 attempts per IP per hour. Resolves former Open Question 5.
  - **Corrected 2026-07-26 after live testing — do not use `adminClient.auth.admin.generateLink({ type: 'signup', ... })` for account creation.** The original design here assumed this call would mirror `invite-co-owner/index.ts`'s `generateLink({ type: 'invite', ... })` and create a user **without** triggering Supabase's own built-in confirmation mailer. A real signup on prod proved that assumption wrong for `type:'signup'` specifically: the user received both Supabase's generic default confirmation email and this feature's branded one for the same signup. `invite` and `recovery` types don't cause this; `signup` does. The actual, working implementation instead: create the account via `adminClient.auth.admin.createUser({ email, password, email_confirm: false, user_metadata: { first_name } })` (a pure admin operation, no email side effect), then call `adminClient.auth.admin.generateLink({ type: 'recovery', email, options: { redirectTo: <verify-email page> } })` to mint the token for our own branded link — the same mechanism the "resend" path below already used safely. As a result, the token type embedded in the confirmation link is always `recovery` now, for both first-time signup and resend; the `signup` token type is no longer produced anywhere.
  - **Enumeration-safe response contract:** because this is public and unauthenticated, the response must not let a caller distinguish "email already has a confirmed account" from "email already has an unconfirmed account" from "brand-new signup" from "recipient is on the suppression list." All of these should return the same generic success-shaped response (e.g. `{ sent: true }`) to the caller. Internally:
    - `createUser()` on an email that already has an `auth.users` row returns an "already registered" error (same `isAlreadyRegisteredError` heuristic `invite-co-owner` already uses, which explicitly covers both `generateLink()` and `createUser()` error shapes) — in that case, do **not** create a duplicate account and do **not** send a new confirmation email to an already-confirmed user; just return the same generic response.
    - If that existing row is unconfirmed (stuck, never finished — same condition `invite-co-owner` detects via `email_has_password()`), this is functionally the same situation as "resend" below — reuse that same internal path rather than building a second one.
  - Builds our own `verify_url` pointing at our real domain (`https://wyskerwatch.com/verify-email?token_hash=...&type=recovery` — bare domain, not `www.`; `www.` redirects to it, see Open Questions resolution below). **Corrected 2026-07-26:** the `isSafeEmailUrl` allowlist in `_shared/email/utils.ts` still defaulted to `www.wyskerwatch.com` even after `APP_URL` was corrected to the bare domain during deployment, which silently broke sending until fixed — its default is now `wyskerwatch.com`.
  - Sends the email via the existing `sendEmail()` using the `verify-email` template, passing `sentByUserId: <new user's own id>` — this is enough for the existing test/demo suppression check to work correctly out of the box (see Schema note above), no special-casing required.
  - Passes a per-request `idempotencyKey` to `sendEmail()` (matching `invite-co-owner`'s `crypto.randomUUID()` pattern) so a render/log failure still leaves a trace — this guards logging, not duplicate-submission; duplicate-submission protection is the rate-limit requirement above.
  - **Partial failure:** if the auth user is created but `sendEmail()` throws (provider down, misconfigured `RESEND_API_KEY`, etc.), the function returns an error to the client, but **does not** attempt to delete the just-created auth user. Reasoning: the user row is harmless while unconfirmed (it can't log in, per Supabase's own confirmation gate), and the resend flow (below) gives a real path to recover once the email problem clears — attempting a compensating delete adds failure-mode complexity (what if the delete itself fails?) for no real benefit.
  - Never logs the plaintext password anywhere (console, `email_logs`, error messages) — the password now transits one additional network hop (browser → this Edge Function → Supabase Auth admin API) versus today's direct `supabase.auth.signUp()` call; this must not become a new place it's incidentally logged.
  - **CORS:** unlike `invite-co-owner`'s `Access-Control-Allow-Origin: '*'` (safe there because that endpoint is authenticated), this endpoint should restrict allowed origins to the app's own known domain(s) — an open CORS policy on a public, privileged, account-creating endpoint is a materially different risk than on an authenticated one.
- **Resend confirmation ("I never got it" / stuck) support** — a small addition to the same Edge Function (decided below: `action: 'resend'` on the one signup function):
  - Calls `generateLink({ type: 'recovery', email })` for the existing-but-unconfirmed user — **not** `{ type: 'signup', email, password }` as the previous draft proposed. `signup`-type link generation only succeeds for an email with no existing `auth.users` row (same constraint `invite-co-owner`'s header comment documents for the `invite` type); for an account that already exists but never confirmed, `recovery` is the correct type, exactly mirroring `invite-co-owner`'s own re-invite branch. This also sidesteps the previous draft's unresolved "where does the resend password come from" gap — `recovery` doesn't need a password at all.
  - Reuses the **existing `verify-email` template** for the resend — the previous draft's proposed new `verify-email-reminder` template is dropped from this revision. Unlike the co-owner/sitter reminder templates (which read as "so-and-so is still hoping you'll..." — framed around a *different person's* pending invite), a resent signup confirmation has no third party to reference; the original template's wording already works unchanged for a second send.
  - `VerifyEmail.jsx` (below) must accept **both** `type=signup` and `type=recovery` in its allowlist, mirroring `AcceptInvite.jsx`'s `ALLOWED_TYPES` pattern, since a resent link uses `recovery`.
  - Same enumeration-safe response shape as signup itself, and same rate-limiting requirement (a "resend" button is otherwise a second, easier-to-hit path to the same spam/cost risk).
- **Decided: don't depend on whether `recovery`-type redemption actually flips `auth.users.email_confirmed_at` — make confirmation explicit and self-controlled instead of assuming an unverified Supabase internal behavior.** `recovery` tokens are designed to let an existing user back in without re-checking confirmation status; they aren't guaranteed to also *set* the confirmation flag the way a `signup`-type token does, and `invite-co-owner`'s existing `recovery` branch doesn't prove it either way (those accounts were created via `invite`-type links, which Supabase treats as pre-confirmed for a different reason). Rather than testing and hoping this holds across Supabase versions/projects, add one more small step:
  - **New, third Edge Function** (e.g. `confirm-email`) — **authenticated**, callable only with a real session JWT (unlike the two above). After `VerifyEmail.jsx` successfully calls `verifyOtp()` (regardless of whether the token was `signup` or `recovery` type) and a session now exists, it calls this function once. The function reads the caller's own `auth.uid()` from their JWT and calls `adminClient.auth.admin.updateUserById(callerId, { email_confirm: true })` on that same id — never on an id supplied by the request body, so a caller can only ever confirm their own account, not anyone else's.
  - This makes email confirmation deterministic regardless of which link type redeemed the session, and is safely idempotent to call every time `VerifyEmail.jsx` runs (a no-op if already confirmed). Resolves former Open Question 6 as a design decision rather than an open risk — no dependency on unverified `recovery`-type side effects remains.

## Repo Findings & Risks

- **Duplicate/overlapping functionality:** None in the "already built" sense — the *pattern* this spec uses (server-side link generation + custom branded email + a same-domain landing page that redeems the token) is a deliberate close copy of what `invite-co-owner/index.ts` + `invite-sitter/index.ts` + `AcceptInvite.jsx` already do. Flagged so it's clear this extends a proven pattern rather than inventing a new one — but see the "Before You Approve This" note above: this endpoint is public/unauthenticated where the invite ones are not, so the security posture can't be copied wholesale, only the token-handling shape.
- **Technical debt nearby:** None new introduced by this spec.
- **Orphaned features nearby:** `verify-email` (this spec's reason for existing) and `welcome` (registered, never called, referenced only in a test file) — `welcome` stays out of scope, flagged for a separate decision.
- **Punch list / known issues in this area:** This spec resolves the P2 item in `docs/launch-punch-list.md`: *"Signup confirmation email isn't branded..."* Check it off and move it to "Resolved" once implemented and verified.

## Non-Goals

- Not touching Google OAuth signup at all.
- Not building a "welcome" email send (the orphaned `welcome` template stays orphaned; a decision on it is separate from this spec).
- Not adding Terms-of-Service acceptance at signup (separate, already-tracked "Not scoped yet" punch-list item).
- Not changing the visual design of the branded email layout itself (`layout.ts`).
- Not implementing Supabase's "Send Email" Auth Hook mechanism, and not implementing dashboard-only branded-template configuration — both alternatives were considered and explicitly not chosen in favor of the code-based, version-controlled approach described here.
- Not designing the specific rate-limiting storage mechanism (a counter table vs. an edge-level solution) — the requirement that one must exist is in scope; the implementation choice is left to implementation time.
- **Decided: no CAPTCHA at launch.** Rate limiting (see thresholds above) is judged sufficient for now; CAPTCHA adds real signup friction for a risk that's currently theoretical. Add it later as a follow-up if `email_logs`/Resend usage actually shows abuse. Resolves former Open Question 1.
- **Decided: `verify-email.ts`'s existing copy stays as-is**, unchanged by this spec. It's serviceable, and a copy-only tweak is cheap to make later (even post-launch) without touching any of the surrounding code — not worth spending implementation time on now. Resolves former Open Question 3.

## Open Questions

Recommend treating it the same as full success from the user's perspective (they do have a working session at that point) while logging the failure server-side for follow-up — but left open since it's a small UX judgment call, not a correctness risk like the others resolved above.

CAPTCHA and leaked-password protection were not enabled on any of the three projects — the leaked-password check added in `sign-up/index.ts` (Have I Been Pwned lookup) now provides more protection here than existed before this feature, not less; CAPTCHA remains a deliberate, known gap per the "no CAPTCHA at launch" decision above. Once the frontend deploy caught up: (1) `isSafeEmailUrl`'s allowed-host default in `_shared/email/utils.ts` was still `www.wyskerwatch.com` after `APP_URL` had been corrected to bare `wyskerwatch.com` during the original deployment, so the branded email's link was rejected as unsafe and failed to send — fixed by updating the default to `wyskerwatch.com`, redeployed (6 functions that share that file: `sign-up`, `resend-webhook`, `clear-email-suppression`, `invite-sitter`, `invite-co-owner`, `send-email`) to all three projects. (2) After that fix, a real signup received **both** Supabase's default confirmation email and the branded one — root cause traced to `auth.users.confirmation_sent_at` being set by `generateLink({type:'signup'})` itself, proving the spec's original assumption (that this call, like `invite-co-owner`'s `type:'invite'`, wouldn't trigger Supabase's own mailer) false specifically for the `signup` type. Fixed by switching account creation to `admin.createUser({email_confirm:false})` (no email side effect) followed by a `type:'recovery'` `generateLink()` call — the same mechanism the resend path already used safely — redeployed (`sign-up` only) to all three projects. See the corrected Technical Spec above for the current implementation. A full real signup → branded email → click-through → signed-in pass was then confirmed working on prod.
