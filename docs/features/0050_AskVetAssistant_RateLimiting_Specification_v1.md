## Before You Approve This

Plain-language flags from the self-review pass:

- **This reuses a mechanism you already built, not a new one.** When the signup form was rate-limited (spec/migration `0039`), a generic "has this key made too many attempts recently" tool was built as its own database table (`rate_limit_hits`) and function (`check_and_record_rate_limit`) — deliberately generic so any other feature could reuse it later without a second table. This spec is that reuse. No new rate-limiting mechanism is being invented.
- **A second, related bug was found while investigating, and you already decided to fix it here.** The three components that talk to the AI chat/insights feature (`PetAIChat.jsx`, `GeneralAskWyskerChat.jsx`, `PetAIInsights.jsx`) have no error handling at all around the AI call. Today, if that call fails for *any* reason (a dropped connection, a server hiccup, and — starting with this spec — a "you've sent too many messages" rejection), the chat just sits there with its loading spinner spinning forever. Nothing tells the owner anything went wrong. Without fixing this, the new rate limit would be invisible to a real user — they'd just see the app hang. This spec fixes it in the same three files.
- **A third, closely related gap — found in the same investigation, and now also included at your request — is fixed here too.** The vaccine and bloodwork document-scanning features (`VaccinationSection.jsx`, `BloodworkSection.jsx`) call the same AI function and share the same new rate limit, but they only stop their loading spinner on failure — they never tell the owner the scan failed at all, so a rate-limited (or otherwise failed) scan looks like it silently did nothing. This spec's first draft flagged this and left it out; this revision fixes it using an existing, already-proven pattern (`VetExport.jsx`'s error toast) rather than inventing a new one.
- **This is a known, already-tracked gap, not a new discovery.** It's the P2 item in `docs/launch-punch-list.md`, originally surfaced while writing spec `0041` (the AI safety-guardrails spec) and deliberately deferred from it at your direction, since it's a cost/abuse issue, not a pet-safety one. This spec is that deferred fix.
- **The limit (20 calls per 10 minutes, per person) is a starting number, not a scientifically derived one.** It's sized to comfortably cover a real chat session, generating insights, and scanning a few pets' vaccine or bloodwork documents back-to-back — while still stopping a runaway script fast. It's easy to change later (two numbers in one file) if it turns out to be too tight or too loose once real usage is seen.

## Functional Requirements

Plain-language description of what needs to happen, beyond what exists today:

1. **Each logged-in person can only ask the AI assistant so many questions in a given stretch of time.** Right now, the only check is "are you logged in at all" — nothing stops one account from asking hundreds of questions per minute. Every single one of those questions is a real, paid request to Anthropic (the company whose AI answers the questions), so unlimited use is a real, growing cost risk once more people are using the app.
2. **When someone hits that limit, they should see a clear, calm message explaining what happened** — not a spinner that never stops, and not a confusing generic error. The message should make clear this is temporary ("try again in a few minutes"), not that something is broken.
3. **A person's ordinary use of the app should never bump into this limit.** A normal chat conversation, generating an insights summary, or scanning several pets' documents in one sitting should all comfortably fit under the cap.
4. **While we're in the code where AI calls can now fail on purpose (the new limit), any other kind of AI failure (a dropped connection, a server problem) should also show a clear message instead of hanging forever** — this closes a real gap that already exists today, independent of the new limit.
5. **The same applies to scanning a vaccine record or bloodwork report photo/PDF** — if that fails (including from the new limit, since scanning uses the same AI budget as chat), the owner should see a clear message that the scan didn't work, instead of the upload button simply going back to normal with nothing having happened.

## Acceptance Criteria

- Given a logged-in owner asks the AI assistant a normal handful of questions in a chat session, when each question is sent, then all of them succeed normally, exactly as today.
- Given a logged-in owner (or a script using their login) sends more than 20 AI requests within a 10-minute window, when the 21st request is made, then it is rejected before any request reaches Anthropic's API (no cost incurred for the rejected request), and the owner sees a clear "you're sending requests too quickly, please wait a bit and try again" message rather than a hang or a generic error.
- Given an owner is rate-limited in one browser tab, when a different logged-in owner uses the AI assistant at the same time, then their requests are unaffected — the limit applies per person, not app-wide.
- Given 10 minutes pass after being rate-limited, when the owner tries again, then their request goes through normally.
- Given the AI call fails for a reason other than the rate limit (e.g. a network problem or a server error), when that happens in `PetAIChat.jsx`, `GeneralAskWyskerChat.jsx`, or `PetAIInsights.jsx`, then the owner sees a clear "something went wrong, please try again" message instead of an indefinitely spinning loading state.
- Given an owner tries to scan a vaccine record or bloodwork document and the AI call fails for any reason (including the new rate limit), when that happens in `VaccinationSection.jsx` or `BloodworkSection.jsx`, then the owner sees a clear error message (toast) telling them the scan didn't work, instead of the upload silently doing nothing.
- Given `npm run build` and `npm run lint`, when run after this change, then both complete with no errors.

## Test Plan

- Normal handful of questions all succeed → **not given its own new Playwright test** — this is unchanged existing behavior already covered by spec `0041`'s existing `e2e/ask-wysker-guardrails.spec.js` tests (which send messages and assert on the reply), which continue to pass unmodified since a normal test run stays well under 20 calls.
- 21st request within 10 minutes is rejected with a clear message, no bypass, no cost → new Playwright test in `e2e/ask-wysker-guardrails.spec.js`: intercept the `ask-vet-assistant` request with `page.route().fulfill({ status: 429, json: { error: '...' } })` (a synthetic 429 response — see below for why a real 21st call isn't used) and assert the rate-limit message renders in the chat instead of a reply, and the loading state clears (no permanent spinner).
- Per-person, not app-wide → **not covered by a Playwright test** — this is enforced entirely server-side by `check_and_record_rate_limit`'s existing, already-battle-tested keying (`rate_key` includes the caller's user ID), the same mechanism spec `0039` already relies on for per-email/per-IP signup limits. Re-verifying that the underlying RPC correctly isolates different keys would be re-testing migration `0039`'s own logic, not this feature.
- Limit resets after the window passes → **not covered by a Playwright test** — would require either waiting 10 real minutes in a test (impractical) or manipulating the database clock, which this repo's suite has no existing pattern for. Covered instead by manual verification against `wysker-watch-dev` before this ships (call the function 21 times via a script, confirm the 21st is rejected and a 22nd succeeds after clearing `rate_limit_hits` rows for that test key).
- Non-rate-limit AI failures show a clear error instead of hanging → new Playwright test: intercept the `ask-vet-assistant` request with a generic failure (`page.route().abort()` or a 500 response), send a message, assert an error message renders and the loading state clears.
- Vaccine/bloodwork scan failure shows a clear error toast instead of failing silently → **not covered by a new Playwright test** — both `VaccinationSection.jsx` and `BloodworkSection.jsx` scan/import flows have no existing Playwright coverage at all today (confirmed via search — no `.spec.js` file references either component), so adding error-path coverage here would mean building first-time test infrastructure for a flow this spec only touches at the error-handling edge, not the core scanning behavior. Verified manually instead: trigger a scan against `wysker-watch-dev` with the rate limit already exhausted (or a temporarily invalid `ANTHROPIC_API_KEY` to force a failure) and confirm the destructive toast appears and the upload input resets.
- **Seeding/access constraints:** None of the new tests need real Anthropic API calls or elevated database access — all use `page.route()` interception against a normal signed-in session (`test1@wyskerwatch.com`), the same pattern spec `0041`'s existing tests in this file already use. The "reject the real 21st call" scenario deliberately does **not** attempt to actually fire 21 real requests in Playwright — doing so would be slow, flaky (shared with whatever else recently called the function from the same test account), and would spend real Anthropic API cost 20 times over just to test the 21st; a synthetic 429 fulfill proves the same client-side handling without any of that.

## Technical Spec

- **Schema:** No new tables or columns. Reuses `rate_limit_hits` and `check_and_record_rate_limit(text, integer, integer)` exactly as they exist today from migration `0039` — no migration needed for this spec.
- **API / Edge Functions:**
  - `supabase/functions/ask-vet-assistant/index.ts`:
    - Add a service-role Supabase client (mirroring the pattern already used in `supabase/functions/sign-up/index.ts`), since `check_and_record_rate_limit` is `service_role`-only by design (revoked from `anon`/`authenticated` in migration `0039`) — the function's existing anon-key client (used only to verify the caller's session) stays as-is alongside it. Requires the `SUPABASE_SERVICE_ROLE_KEY` secret, which this project's other privileged functions (`sign-up`, `invite-co-owner`, etc.) already have configured in all three Supabase projects — no new secret to provision.
    - After confirming the caller is authenticated (existing check, unchanged) and before making any Anthropic API call, call `check_and_record_rate_limit` with `p_key = 'ask-vet-assistant:user:' + userId`, `p_limit = 20`, `p_window_seconds = 600` (10 minutes). If it returns `false`, respond `429` with `{ error: "You've reached the limit for AI requests. Please wait a few minutes and try again." }` (double-quoted in actual code, to allow the apostrophe) and stop — no Anthropic call is made, so a rejected request costs nothing.
    - If the RPC call itself errors (e.g. the database is unreachable), fail closed — same posture `sign-up/index.ts` already takes for its own rate-limit RPC failure (respond `503`, don't proceed to the paid API call) — rather than silently skipping the limit.
    - Constant limit/window values declared at the top of the file (mirroring `sign-up/index.ts`'s `EMAIL_RATE_LIMIT`/`RATE_WINDOW_SECONDS` pattern) so they're easy to find and adjust later without touching logic.
  - No change to the CORS handling — the function stays wide-open (`Access-Control-Allow-Origin: '*'`), consistent with `_shared/cors.ts`'s own documented rule that this is acceptable for functions that already require a valid session (unlike the public, unauthenticated `sign-up`/`confirm-email` functions, which use the stricter `scopedCorsHeaders()`).
- **Components/files touched:**
  - `src/api/aiClient.js` — `invokeAI()`'s existing error path (`if (!resp.ok) throw new Error(...)`) is changed to throw an error object that also carries the HTTP status (e.g. `Object.assign(new Error(...), { status: resp.status })`), so calling components can distinguish "rate limited" (429) from any other failure without re-parsing the response body themselves.
  - `src/components/PetAIChat.jsx` — `send()`'s `invokeAI` call is wrapped in `try/catch`; on error, pushes a message rendering inline chat-bubble text: the specific rate-limit copy from the Edge Function's `429` body if `err.status === 429`, otherwise a generic "Something went wrong. Please try again." `loading` is reset in a `finally` block so it can never get stuck `true`.
  - `src/components/GeneralAskWyskerChat.jsx` — identical treatment to `PetAIChat.jsx`.
  - `src/components/PetAIInsights.jsx` — `generateInsights()`'s `invokeAI` call is wrapped in `try/catch`; on error, sets a new `error` state (parallel to the existing `urgent` state) and renders inline text ("Something went wrong generating insights. Please try again." or the specific rate-limit message), reusing the existing "Analyze {pet.name}'s Records" button to retry rather than a new control. `loading`/`generated` reset in `finally` so the retry button reappears correctly.
  - `src/components/VaccinationSection.jsx` — `handleScan()`'s existing `try/finally` (uploads the photo, calls `invokeAI`, matches/saves scanned vaccines) gains a `catch` block: shows `toast({ variant: 'destructive', description: ... })` with the specific rate-limit message if `err.status === 429`, otherwise "Couldn't scan this document. Please try again." Requires adding `useToast` (not currently imported in this file) — same import `VetExport.jsx` already uses. The existing `finally` (resets `scanning` and clears the file input) is unchanged, so the button already correctly returns to normal either way; this only adds the missing message.
  - `src/components/BloodworkSection.jsx` — identical treatment to `VaccinationSection.jsx`: `handleImport()`'s existing `try/finally` gains a `catch` block with the same toast pattern, `useToast` newly imported.
- **Design System compliance:** Checked against `docs/foundation/0005 Design System.md` including its Amendments. No new visual pattern — the chat-bubble error message reuses `AIEmergencyNotice.jsx`'s existing slot/treatment in the message list (different copy/icon, same structure), and the Insights error text reuses `InsightSummaryCard.jsx`'s existing inline-text-instead-of-content pattern. No conflict found.
- **Constraints from CLAUDE.md / locked decisions:** No conflict. Backend changes here (none — no migration, just an Edge Function code change) still need pushing to all three Supabase projects (dev/staging/prod) per `CLAUDE.md`'s existing deploy note, since Edge Function code isn't picked up by the frontend build pipeline. No database schema change means no new migration to run against `wysker-watch-restore-scratch` risk — that project stays untouched, as required.

## Non-Goals

- A per-IP rate limit layer (in addition to per-user) — unlike the public, unauthenticated `sign-up` function (which needs an IP-based limit because it has no logged-in caller to key on), `ask-vet-assistant` already requires a real Supabase session for every call, so per-user keying alone is the right control here; adding IP-based limiting on top wouldn't stop a determined single account and would only add complexity.
- Any UI showing the owner their remaining quota/how many requests they have left before hitting the limit — out of scope; the message only appears once the limit is actually hit.
- Making the limit configurable per-environment or admin-adjustable at runtime — the limit is a constant in the Edge Function code for now, changeable by editing and redeploying, consistent with how `sign-up/index.ts`'s own rate limits are managed today.
- Any change to the AI guardrails (emergency detection, urgent-flag backstop, disclaimer) built in spec `0041` — untouched by this spec.
