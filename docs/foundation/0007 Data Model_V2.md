Purpose

This document defines the canonical data model for Wysker Watch as it actually exists in the Supabase/Postgres schema today. It supersedes `0007 Data Model_V1.md` (moved to `Old/`), which described an 11-table schema that predates Pet Onboarding, Co-Owners, Analytics, Account Types, and the entire Daily Check-In / Observation / Wellness Score / Baseline system. V1 is out of date and should not be used as a reference.

Wysker Watch uses a relational, owner-scoped schema built on Supabase/Postgres with strict Row Level Security (RLS).

1. Design Principles

- Owner-Scoped: every pet-linked table is readable/writable only by the pet's owner or co-owner, via `auth.uid()`.
- Relational: all relationships use real foreign keys with `on delete cascade` from `pets`.
- Records belong to the pet: a record's `created_by` (who entered it) is cleared, not deleted, when that account is deleted, on all 13 record tables (migration 0058, spec 0075). Since migration 0062 (spec 0083, PA-25) the database sets it: on the 12 record tables (all but `pet_co_owners`), a signed-in person's insert is stamped with `auth.uid()` whatever the app sends, and an update keeps the original author (`stamp_record_author()`). Server routines (no user session) aren't limited, so account deletion still clears it.
- Shared owner check: every pet-scoped table's RLS uses a single `is_pet_owner(pet_id, user_id)` SQL function (migration 0004) rather than duplicating owner-or-co-owner logic per table. Since migration 0059 (spec 0077) it returns false unless `user_id` is the signed-in person, and like every function in `public` it's runnable only by the roles its migration grants (signed-in users for access-rule helpers, the server for everything else). Server-side code that needs to ask about another user uses `deletion_user_owns_pet` (0058).
- Baseline-Driven: the schema supports both a legacy, form-based baseline (`pet_onboarding`) and a newer, generalized per-metric baseline model (`pet_baselines`) — see section 6.
- Two independent daily signals, never blended: `daily_check_ins.status` is a subjective, owner-reported **Vibe** (`great`/`off`/`tough`/`skipped`), and `daily_check_ins.symptom_count` is an objective, unweighted count of distinct symptoms logged that day across `observations`. Per Product Principle 6 ("Missing Data Is Meaningful"), `skipped` is itself a real, distinct answer, not an absence of one. (This replaced an earlier `normal`/`changed`/`skipped` enum and a computed 0–100/0–10 wellness score — see §3.14.)
- One logging system: Daily Check-In/Observations (migration 0014) was first added alongside the older `symptom_logs`. Since migration 0061 (spec 0081) the older tables are gone and `observations` holds everything, weight included. See section 7.

3. Table Definitions

3.1 profiles
Extends `auth.users`.
- `id` uuid PK, references `auth.users(id)` on delete cascade
- `role` text, default `'user'`, check in (`admin`, `user`)
- `email` text — a copy of the login email, written once at signup; read-only outside the service role since 0057 (invites match the login email instead)
- `account_type` text, default `'production'`, check in (`production`, `test`, `demo`, `owner`) — added 0010 (`owner`, a real personal-use account, added 0025; never assigned by the allowlist), auto-classified by email allowlist (`classify_account_type()`) at signup. Allowlist as of migration 0053: `test1@`/`test2@`/`test3@`/`test4@`/`coowner1@`/`coowner2@`/`petsitter1@`/`petsitter2@wyskerwatch.com` → `test`, `demo1@wyskerwatch.com` → `demo`, everything else → `production`. test4@ (0051) is the e2e sitter fixture; the coowner/petsitter inboxes (0053, spec 0070) are for manual invite testing. Emails *sent by* a `test`/`demo` account are suppressed (`sendEmail.ts`). `test3@` was added in migration 0049 specifically as a `profiles.role='admin'` Playwright fixture (spec 0053) — see CLAUDE.md's e2e note before reusing `test1@`/`test2@` for anything role-sensitive.
- `first_name` text, max 100 chars — added 0015; populated at signup from auth metadata when provided, otherwise self-editable (covered by the existing `profiles_update_own` policy, no RLS change needed)
- `last_name` text, max 100 chars — added 0017, same pattern as `first_name`
- `timezone` text, nullable — added 0017; populated client-side on first authenticated load via `Intl.DateTimeFormat` detection (`src/lib/timezone.js`), not backfilled for existing rows. Enforced to be a valid IANA identifier by a `BEFORE INSERT/UPDATE` trigger checking against Postgres's own `pg_timezone_names` catalog (a CHECK constraint can't do this, since checks can't query other relations) — this matters because RLS alone only restricts *who* can write a profiles row, not *what* value they write, so without the trigger a direct REST API call could store an arbitrary string.
- `timezone_is_manual` boolean, default `false` — added 0017; once a timezone is set (auto-detected or manually chosen), the app never silently overwrites it again. This is enforced in application code (`shouldAutoPopulateTimezone()` in `timezone.js`), not the database, same as the read side of `first_name`.
- `terms_accepted_at` timestamptz, nullable — added 0047; when Terms of Service/Privacy Policy agreement was recorded at signup. Null for any account created before this shipped — existing users are never retroactively asked to agree to anything.
- `terms_version` text, nullable — added 0047; the Terms of Service "Last updated" string in effect at the moment of signup.
- `privacy_version` text, nullable — added 0047; same idea for the Privacy Policy, stored as a separate column since the two documents version independently.
- `marketing_opt_in` boolean, default `false` — added 0047; answer to a separate, always-optional marketing-communications checkbox at signup. Currently unused — no marketing-email sending capability exists anywhere in the app yet; this only captures the answer for whenever that's built.
- `created_at`, `updated_at` timestamptz

`role` and `account_type` can only be changed by a service-role process (trigger-enforced, migration 0011) — a regular authenticated user cannot self-promote to admin or test/demo.

3.2 pets
Central entity for all health data.
- `id` uuid PK
- `created_by` uuid, references `auth.users(id)` — the primary owner (original creator); permission checks use `is_pet_owner()`, not this column directly, once a pet has co-owners. No signed-in user can change it (migration 0062, `protect_record_creator()`); only the server's hand-off (`transfer_pet_ownership()`, 0058) does. The same lock applies to `pet_sits.created_by`.
- `species` text, default `'Cat'`, check in (`Cat`, `Dog`)
- `name` text, max 100 chars
- `photo_path` text — the photo's location in the private `uploads` bucket (e.g. `{userId}/…`, or `shared/…` for stock demo photos), shown through a short-lived signed link. Replaced the public `photo_url` (spec 0071: added 0054, `photo_url` dropped 0055). Since migration 0062 (spec 0083, PA-73) a signed-in person can only set it to null, `shared/<name>`, or `<their own id>/<name>`; leaving it unchanged is always allowed (`protect_pet_photo_path()`). `delete-pet` and `reset-sandbox-account` keep any file another pet still uses as a photo or document (`_shared/petPhoto.ts`).
- `breed` text
- `birth_date` date (not future), `birth_date_precision` text, default `'UNKNOWN'`, check in (`EXACT`, `MONTH_YEAR`, `YEAR`, `UNKNOWN`)
- `conditions`, `nicknames`, `favorite_activities` text[], default `{}`
- `medications` text — free-text field, distinct from the `medications` table (legacy, still present)
- `notes` text, max 500 chars
- `is_memorial` boolean, `memorial_date` date
- `sex` text, check in (`Female`, `Male`, `Unknown`) — added 0008
- `altered_status` text, check in (`Yes`, `No`, `Unknown`) — added 0008
- `gotcha_date` date (not future), `gotcha_date_precision` text — added 0008
- `microchip_number` text, max 50 chars — added 0008
- `akc_registered` boolean, `akc_registered_name`, `akc_registration_number`, `breeder` text — added 0008
- `color_markings` text — added 0042; purely descriptive, shown on the merged Pet Information onboarding step (spec 0029), no overlap with any other tracked value
- `created_at`, `updated_at` timestamptz

Life stage (Kitten/Puppy, Adult, Senior) and display age are derived at read time from species + birth_date + birth_date_precision (`src/lib/lifeStage.js`) — never stored, so they can't go stale.

3.6 vaccinations
`id`, `created_by`, `pet_id`, `vaccine_name`, `date_given`, `next_due_date`, `administered_by`, `lot_number`, `notes`, timestamps.

`id`, `created_by`, `pet_id`, `date`, `lab_name`, `vet_name`, plus numeric lab values (`bun`, `creatinine`, `sdma`, `phosphorus`, `potassium`, `sodium`, `calcium`, `hematocrit`, `hemoglobin`, `total_protein`, `albumin`, `alt`, `ast`, `alkaline_phosphatase`, `total_bilirubin`, `glucose`, `t4`), `urine_specific_gravity`, `urine_protein` (enum), `notes`, `created_at`.

3.8 symptom_logs
Dropped in migration 0061 (spec 0081); data not moved; the nightly backup keeps a copy for 30 days.

3.9 pet_sits / 3.10 pet_sit_logs / 3.11 pet_sitter_access
Sitter session model. `pet_sits` covers multiple pets via a `pet_ids uuid[]` array (not a single FK) plus dates/instructions/contacts. `pet_sit_logs` are entries a sitter makes during a session. `pet_sitter_access` grants a sitter (by email, linked to `sitter_user_id` on login) read/log access scoped to one `pet_sit`. That linking step (`claim_pending_sitter_invites()`, migration 0028, called from `AuthContext.jsx` the same way `claim_pending_co_owner_invites()` already was) actually runs now — until 2026-07-24 it was documented intent that nothing in the code ever implemented, the same failure mode `pet_co_owners.co_owner_user_id` had before migration 0016 fixed it. `pet_sitter_access` also picked up a `created_by` column in migration 0029 (every other table's generic insert path requires one; this table was missing it since 0001, which silently broke every insert until fixed). Migration 0057 (spec 0073): sitters see a sit's pets, photos, check-ins, observations and checklist only from the day before `start_date` through the day after `end_date`, on the owner's calendar (the sit creator's `profiles.timezone`, UTC if unset). That rule lives only in `pet_sit_is_open()`, which `is_pet_sitter()` and `is_pet_sit_sitter()` both call; both now answer only about the caller. Only `claim_pending_sitter_invites()` can link an account to an invite. A pet deleted outside `delete-pet` leaves behind sits nobody can edit; `delete-pet` removes the pet from its sits first.

Account deletion (migration 0058, spec 0075): `pet_sitter_access.sitter_user_id` is `ON DELETE CASCADE`. A sitter who deletes their account loses the invite, so re-registering with the same email doesn't bring access back through `claim_pending_sitter_invites()`. `pet_sit_logs.created_by` is `SET NULL`, so a departed sitter's notes stay. When an owner deletes their account or removes a shared pet, their sits covering a surviving pet are handed to the new primary owner or ended (see `transfer_pet_ownership()` in §5).

3.12 pet_co_owners
Full-parity co-ownership (migration 0004) — distinct from sitter access. `id`, `pet_id`, `owner_id` (the primary owner who invited), `created_by`, `co_owner_email`, `co_owner_user_id` (filled once accepted), `created_at`. Once linked, a co-owner can edit the pet and add, edit and delete its records via `is_pet_owner()`, like the primary owner. Since migration 0062 (spec 0083, PA-24), no signed-in user, co-owner or primary owner, can delete a `pets` row directly or change `pets.created_by`: a pet is deleted only through the `delete-pet` function, which hands it to a co-owner, removes only a co-owner's own access, or deletes it for good (spec 0083 D5). Only the primary owner can invite/remove co-owners (enforced by the database since migration 0056; see below).

Access fix (migration 0056, spec 0072, punch list PA-02): 0004's insert rule only checked `auth.uid() = owner_id`, so any signed-in user who knew a pet's ID could insert a row naming themselves as both inviter and `co_owner_user_id`, gaining full owner rights through `is_pet_owner()`, invisibly to the real owner. 0056 replaces all three policies. **Insert** requires `is_primary_pet_owner(pet_id, auth.uid())` (a new `security definer` helper: is the caller `pets.created_by`? callable by signed-in users only), `owner_id = auth.uid()`, `created_by = auth.uid()`, and `co_owner_user_id is null`, so `claim_pending_co_owner_invites()` is the only way an account is linked. **Select** is `is_pet_owner(pet_id, auth.uid()) or co_owner_user_id = auth.uid()`: every owner sees the full list. **Delete** is `is_primary_pet_owner(pet_id, auth.uid())`. Access checks no longer use `owner_id`, because it goes stale after an ownership transfer (delete-pet/delete-account update it by hand); the column is kept. There is still no update policy, deliberately. A co-owner leaving goes through delete-pet's service-role path, unaffected.

Account deletion (migration 0058, spec 0075): `created_by` is nullable and `ON DELETE SET NULL`, so the co-owner invites a primary owner sent no longer vanish when they leave. When a primary owner deletes their account or removes the pet, `transfer_pet_ownership()` promotes the oldest linked co-owner, deletes only that person's row, and repoints every other row's `owner_id`/`created_by` to them.

Bug fix (migration 0016): `co_owner_user_id` was documented as "filled in once the invited person signs up/logs in with this email" but nothing ever actually set it — the invite dialog only ever inserted `co_owner_email`, and there was no `UPDATE` policy on this table at all. Consequences while the bug was live: an invited co-owner never actually gained access (since `is_pet_owner()` checks `co_owner_user_id`), and `delete-pet`'s ownership-transfer branch never fired (it only triggers for co-owners with a non-null `co_owner_user_id`), so deleting a "shared" pet always silently took the permanent-delete path instead of transferring ownership. Fixed by `claim_pending_co_owner_invites()`, a `SECURITY DEFINER` function the client now calls once per session (login/session restore) that links any pending invite matching the signed-in user's email.

3.13 pet_onboarding
One row per pet — the "Complete {Pet}'s Profile" wizard's progress and initial behavioral baseline. `id`, `created_by`, `pet_id` (unique), `health_status`, `medications_status`, `appetite_baseline`, `water_baseline`, `energy_baseline`, `mobility_baseline`, `bathroom_baseline` (all enums), `current_step` (enum, tracks wizard resume point — `vaccinations` and `review` steps added 0041, spec 0029's Onboarding Refresh, ahead of `completed`), `completed_at`, `skipped_at` (added 0013 — distinguishes "explicitly skipped" from "interrupted mid-flow," per Product Principle 6), timestamps. Diagnoses are NOT duplicated here — the wizard's "Known Conditions" card writes directly to `pets.conditions`.

3.14 daily_check_ins
One row per pet per day. `id`, `created_by`, `pet_id`, `check_in_date`, `status`, `completed_at`, `source` (`app`/`notification`/`widget`/`sitter`/`catch_up`, `catch_up` added migration `0033`), `notes`, `symptom_count` int (added 0026), timestamps. Unique on `(pet_id, check_in_date)`.

`source = 'catch_up'` marks a day authored through the Catch-Up Check-In flow (single-day or multi-day, `0015_MultiDay_CatchUp_CheckIn_Specification_v1.md`) rather than logged live that same day — distinguishes a real-time entry from one backfilled possibly days or weeks after `check_in_date`.

`status` is `great`/`off`/`tough`/`skipped` as of migration `0026_vibe_and_symptom_count.sql` — the original `normal`/`changed`/`skipped` enum from migration 0014 was renamed in place (`normal`→`great`, `changed`→`off`, plus a new `tough` value; `skipped` unchanged), with existing live rows remapped by the migration itself. `symptom_count` is a persisted integer — the total count of distinct symptoms logged that day across all 11 counted `observations` categories, computed once at check-in time rather than derived live on every read. Some rows migrated from the pre-0026 era have a real `symptom_count` but a null `status` (`0027_migrate_symptom_logs_to_checkins.sql`) — code that reads this table needs to handle that combination, not just null-vs-populated on either field independently.

As of migration `0034_save_daily_check_ins.sql` (2026-07-25, spec `0016`), writes to this table via the Daily Check-In flow go through `public.save_daily_check_ins()`, a Postgres function (a stored, reusable batch of SQL commands the database itself runs) called with `security invoker` — meaning it runs with the calling user's own permissions, not elevated ones, so the RLS policies below still apply exactly as before. The function upserts the check-in row, clears its prior `observations` rows, and inserts the new ones for a batch of one or more days in a single database transaction (all-or-nothing) — replacing the previous approach of several separate, independently-failable client calls.

Migration `0046_save_daily_check_ins_conflict_detection.sql` (spec 0043) extended this same function with an optional per-day `expected_updated_at` check: a caller can assert "this is the `updated_at` I loaded before starting this edit," and if the row has since changed (a different co-owner saved first), the function refuses to overwrite it and instead returns `{ conflict: true, check_in, observations }` describing what's actually saved, rather than silently clobbering it. Omitting `expected_updated_at` entirely (still the default for Catch-Up's bulk multi-day save) skips the check, same overwrite behavior as before this migration.

3.15 observation_types / 3.16 observation_options
Reference data (not owner-scoped; readable by any authenticated user, writable only by migration/service role). 14 seeded types as of migration 0026: appetite, water_intake, bathroom, stool, vomiting, **nausea** (added 0026), energy, mobility, breathing, itching, behavior, medication_exception, weight, other. Each type has `category`, `species_applicability` (`cat`/`dog`/`both`), `answer_type` (`enum`/`number`/`text`/`boolean`), `baseline_supported`, `score_supported`, `sort_order`. Each enum type has seeded `observation_options` rows with a `severity_score` column — **this column is vestigial as of migration 0026**: it's still populated on insert and still present in the schema, but nothing in `src/lib/checkin/scoring.js` reads it anymore (the Vibe/Symptom-Count model is unweighted — every logged symptom counts equally, there is no deduction). `src/lib/checkin/config.js` is the client-side mirror of the current (unweighted) attribute model used to render the Daily Check-In UI; it does not mirror `severity_score`.

3.17 observations
The actual owner-reported observations — primary truth for the Daily Check-In system. `id`, `created_by`, `pet_id`, `daily_check_in_id` (nullable FK), `observation_type_id`, `value`, `numeric_value`, `severity_score` (vestigial, see §3.15), `notes`, `observed_at`, timestamps. (`photo_url` was dropped in migration 0054, spec 0071: no screen ever set or showed it.) Since spec 0081 this is also weight's only home: type `weight`, `numeric_value` in lbs, with or without a check-in (see §7).

3.18 pet_baselines
Generalized per-metric baseline, one active row per `(pet_id, observation_type_id)` (enforced by a partial unique index where `effective_to is null`), with history preserved via `effective_from`/`effective_to` rather than overwrite. `id`, `created_by`, `pet_id`, `observation_type_id`, `baseline_value`, `baseline_numeric_value`, `baseline_notes`, `confidence_level` (`low`/`medium`/`high`), `source` (`onboarding`/`manual_edit`/`system_suggested`), `effective_from`, `effective_to`, timestamps.

Note: this table exists but is not yet populated or read by any UI. There is currently no baseline row for `weight` (or any metric) actually written anywhere in the app (weight itself is written, to `observations`, see §7; it just has no baseline) — `pet_onboarding`'s baseline columns (appetite/water/energy/mobility/bathroom) are the only baseline data actually in use today, and they are a fixed enum-based form, not rows in `pet_baselines`. Any feature that wants to compare "today vs. baseline" for weight or another `observation_types` metric needs to either start writing to `pet_baselines` or accept there is no baseline to compare against yet.

3.19 wellness_scores
Dropped in migration 0061 (spec 0081); data not moved; the nightly backup keeps a copy for 30 days.

3.20 analytics_events
First-party event log (no third-party analytics provider wired up). `id`, `user_id`, `event_name`, `properties` jsonb, `created_at`. Insert/select restricted to the event's own `user_id`. A nightly/hourly `pg_cron` rollup (migrations 0023/0024) aggregates this into `analytics_daily_summary` (DAU, new/returning users, check-in funnel counts) — SQL-Editor/owner access only, not exposed via the Data API. Migration `0043_analytics_exclude_test_accounts.sql` (spec 0030) changed `compute_daily_analytics_summary()` to exclude events tagged `account_type: 'test'` in `properties` (`test1@`/`test2@`/`test3@wyskerwatch.com` as of migration 0049 — see §3.1) from every rollup metric, and fixed `checkins_completed` to count the current `vibe_recorded` event instead of two retired event names; existing summary rows were backfilled with the corrected logic in the same migration. Full event catalog, rollup behavior, and a known rollup bug are documented in `docs/features/Analytics Feature.md`. This table is not a database backup — the project currently has no database backup or point-in-time recovery configured at all (`pitr_enabled: false` on the live Supabase project), a real and separate open risk.

3.21 notifications
In-app notification list (migration 0005 — present since early in the schema's history, but missed in the original pass of this document; now actively read by the Notifications screen). `id`, `user_id`, `type` text (e.g. `ownership_transfer`), `message` text (human-readable, shown as-is in the UI), `read` boolean default `false`, `created_at`. No email is sent from this table — it's purely an in-app list, surfaced via `src/lib/notifications/notificationClient.js` (`getUnreadCount`, `listNotifications`, `markRead`, `snoozeNotification`, `markAllRead`, `clearNotifications` / `planClear`). The app never deletes a `vaccination_due` row; it marks it read instead, since `generate_vaccination_due_notifications()` treats a missing row as never sent (spec 0076). Rows are inserted by Edge Functions using the service-role client (e.g. `delete-account` generates an `ownership_transfer` notice for a co-owner when the primary owner's account is deleted), which bypasses RLS — there is intentionally no client-side insert policy. Users can `select`/`update` (mark read) / `delete` only their own rows (`user_id = auth.uid()`).

Migration `0044_vaccination_due_notifications.sql` (spec 0034) added four columns — `related_type` text, `related_id` uuid, `stage` text, `snoozed_until` timestamptz — and an indexed `(related_type, related_id)` pair, so a reminder can be deduplicated/escalated/snoozed instead of being a one-off message. The same migration adds `public.generate_vaccination_due_notifications()`, a `security definer` function (same elevated-privilege rationale as `compute_daily_analytics_summary`, since it reads across every user's pets/vaccinations/notifications) run daily at noon via `pg_cron`. It notifies the primary owner and every linked co-owner (never pet sitters) at escalating stages (`30_day`/`14_day`/`7_day`/`3_day`/`due_today`/`overdue`) as a vaccination's `next_due_date` approaches, superseding rather than duplicating an still-unread reminder at an earlier stage, and skipping regeneration entirely while an existing reminder is within its `snoozed_until` window.

Types written by account and pet deletion (migration 0058, spec 0075): `ownership_transfer`, `co_owner_removed`, `pet_sit_transferred`, `pet_sit_pet_removed`, `pet_sit_cancelled`. The Notifications screen shows `message` as stored, whatever the type.

3.22 email_logs
Delivery record for every transactional email attempt made through the shared `sendEmail()` service (migration 0018, extended by 0019/0032/0038 — present since 2026-07-08 but never added to this document until now, a gap this document's own revision history had already flagged). `id`, `recipient_email`, `template_name`, `status` text, check in (`pending`, `sent`, `suppressed`, `failed`), `provider_message_id`, `error_code`, `error_message`, `related_entity_type`/`related_entity_id` (polymorphic link back to whatever triggered the send, e.g. a `pet_co_owners` invite row), `idempotency_key` (unique where non-null — lets a retried send replay its original result instead of sending twice), `sent_at`, `created_at`. Migration 0038 added three delivery-lifecycle columns, filled in later and asynchronously by the `resend-webhook` Edge Function once Resend reports what actually happened to a sent message: `delivered_at`, `bounced_at`, `complained_at` timestamptz. These sit alongside `status` rather than replacing it — `status` reflects the outcome at send time, the three new columns layer the later delivery lifecycle on top, and `delivered_at`/`complained_at` can both be set on the same row (a message can be delivered, then later reported as spam — they're independent facts, not mutually exclusive states). Written exclusively by Edge Functions via the service-role client; RLS enabled with zero policies, so every other role is denied both select and insert by default. See `docs/features/requirements-transactional-email.md` and `docs/features/0020_Resend_Bounce_Delivery_Webhook_Specification_v1.md`.

3.23 resend_webhook_events
Dedup ledger for the `resend-webhook` Edge Function (migration 0038): `event_id` text primary key, `event_type`, `provider_message_id`, `received_at`. Resend (via its Svix-based webhook delivery) can redeliver the same event more than once on a slow/failed response; this table lets the webhook recognize and skip a repeat without reprocessing it. Service-role only, RLS enabled with zero policies. No automatic retention/cleanup — rows are small and low-volume.

3.24 email_suppressions
Durable per-address block list (migration 0038): `id`, `email` unique, `reason` text, check in (`bounced`, `complained`), `created_at`, `cleared_at`, `cleared_by`, `cleared_note`. A hard bounce or spam complaint reported by Resend adds a row here (via `resend-webhook`); `sendEmail()` checks this table before every send and skips Resend entirely for an address with an active (uncleared) row. Rows are never deleted — clearing (via the `clear-email-suppression` Edge Function) sets `cleared_at`/`cleared_by`/`cleared_note` rather than removing the row, so there's always a record that an address was once suppressed even after being cleared. A soft/temporary bounce does not add a row here — only Resend's permanent-failure `email.bounced` event and spam complaints do. Service-role only, RLS enabled with zero policies. See `docs/features/0020_Resend_Bounce_Delivery_Webhook_Specification_v1.md`.

3.25 rate_limit_hits
Generic abuse/cost guard for public, unauthenticated Edge Functions (migration 0039). `id`, `rate_key` text (an opaque key — an email address, a request IP, or a composite like `beta-signup:email:x@y.com`, so one table serves any number of independently-limited call sites), `created_at`. No owner scoping — service-role only, RLS enabled with zero policies. Read and written exclusively by `public.check_and_record_rate_limit(p_key, p_limit, p_window_seconds)` and its multi-key sibling `check_and_record_rate_limits(p_keys, p_limits, p_window_seconds)`, both `security definer`, execute revoked from `public`/`anon`/`authenticated` and granted only to `service_role`. Each call atomically checks whether `p_key` is still under `p_limit` attempts within the trailing `p_window_seconds` and, if so, records this attempt in the same call; a rejected attempt is not itself recorded. Opportunistically prunes rows older than the window on every call. Used by `sign-up` (migration 0039), `ask-vet-assistant` (spec 0050), and `beta-signup` (spec 0053, migration 0048) — see CLAUDE.md before assuming a new abuse-prone public endpoint needs its own rate-limit mechanism built from scratch.

3.26 beta_signups
Email + 4-question screener capture from the public `/beta` landing page (migration 0048, spec 0053) — not a real Wysker Watch account, a separate lightweight pre-auth capture. `id`, `email` text, `condition_status` text, `tracking_method` text, `frustration` text (open-ended), `beta_comfort` text, `reviewed_at` timestamptz (null until manually marked reviewed on the admin page), `created_at`. Inserted exclusively by the `beta-signup` Edge Function via the service-role client, after that function verifies a Cloudflare Turnstile CAPTCHA token and checks `rate_limit_hits` (§3.25) — no insert policy exists for `anon`/`authenticated`, same as every other service-role-only table above.

Unlike those other service-role-only tables, this one is also directly readable and updatable by a real logged-in user: `select`/`update` are granted to `authenticated` where `profiles.role = 'admin'` (checked via a subquery against `profiles`, not a separate helper function). This is the **first** admin-gated RLS policy in the schema — see §5.

5. RLS Model

Every pet-scoped table's policies are `is_pet_owner(pet_id, auth.uid())` (migration 0004's `security definer` function), which returns true if the calling user is either the pet's `created_by` or a linked row in `pet_co_owners`. This means co-owners have full parity with the original owner everywhere, including delete, by design. Sitter access is a narrower, separate grant: read access to `pets`/`pet_sits`/`pet_sit_logs`/`daily_check_ins`/`observations` (0030/0031/0045), plus adding checklist entries, all limited to the sit's window (day before start through day after end, owner's calendar, migration 0057). Sitters can't edit or delete any of these (letting them tick the checklist is PA-60). `observation_types`/`observation_options` are the only pet-adjacent tables with no owner scoping — they're global reference data. `profiles.role`, `profiles.account_type` and `profiles.email` can only be changed by a service-role process, never by the user themself.

Server-only deletion functions (migration 0058, spec 0075): `transfer_pet_ownership(p_pet_id, p_from_user, p_reason)` is the one routine for passing a pet to a co-owner, used by `delete-pet` and `delete-account`. `prepare_account_deletion(p_user_id, p_folder_paths)` does every database step of deleting an account in one transaction and returns the storage files to delete. Both are `security definer` and can be run only by `service_role` (`execute` revoked from `public`, `anon` and `authenticated`).

Non-pet-scoped tables split into two patterns. The older/more common one is service-role-only: `email_logs`, `resend_webhook_events`, `email_suppressions`, `rate_limit_hits` (§3.25) all enable RLS with zero policies at all, so every non-service-role caller (including a normal logged-in user) is denied both select and insert by default — only an Edge Function's service-role client can touch them. `beta_signups` (§3.26, migration 0048) introduces a second, newer pattern: still no policy for `anon`/plain `authenticated` inserts (same service-role-only write path), but with an added `select`/`update` policy scoped to `authenticated` users where a subquery against `profiles` confirms `role = 'admin'`. This is the first table in the schema where a real user session (not a service-role Edge Function) is trusted to read privileged data directly, gated by role rather than ownership — worth knowing before assuming every non-pet-scoped table follows the older all-or-nothing pattern.

6. Baseline Model — current state (important, since two systems exist)

There are two baseline mechanisms in the schema right now, at different levels of maturity:

- `pet_onboarding` — fixed-form baseline (health status, medications yes/no, appetite/water/energy/mobility/bathroom), captured once during onboarding and editable afterward. `BaselineSection.jsx` and the Pet Profile "Baseline" card read/write it directly; as of spec `0031`, Ask Wysker (`AskWyskerSheet.jsx`/`PetAIChat.jsx`/`PetAIInsights.jsx`) also reads it to ground AI responses in the pet's actual baseline.
- `pet_baselines` — a generalized, per-`observation_type` baseline model with confidence levels and history, built in migration 0014 alongside Daily Check-In. As of this document, it is schema-only: nothing writes to it and nothing reads from it. There is no weight baseline, no appetite baseline via this table, nothing.

Any new feature (e.g. Insights) that wants a true "compared to baseline" comparison must either (a) start populating and reading `pet_baselines`, or (b) explicitly document that it's using a weaker proxy (e.g. "compared to the last logged entry") until that table is wired up. Do not assume a baseline value exists for any metric without checking.

7. Weight — current state (spec 0081, migration 0061)

There is one logging system. The old second one, `symptom_logs` (migration 0001), was dropped in migration 0061 along with `wellness_scores` and `food_logs`; migration 0027 had already moved its answers into check-ins. The Daily Check-In flow writes `daily_check_ins` + `observations` only.

Weight lives only in `observations`, type `weight`, value in lbs in `numeric_value`. A weight row is one of two kinds:

- **Inside a check-in:** typed in the check-in's Weight box. It has a `daily_check_in_id` and is dated by that check-in's `check_in_date`.
- **On its own:** logged outside a check-in (the Log weight sheet, onboarding, a ticked bloodwork-import weight). `daily_check_in_id` is null, and the day is stored in `observed_at` as noon UTC of the chosen day, read back as the UTC date. A standalone weight never creates a check-in. There is no separate date column (spec 0081 Amendment 1).

There is one weight per pet per day. The app keeps it that way on every write; where older data has more than one weight on a day, the day's weight is chosen like this: a standalone weight beats a check-in weight, then the later `updated_at`, then the larger `id`. Values outside 0.1–300 lbs are skipped. The app (`src/lib/weightClient.js`) and the server (`supabase/functions/_shared/weight.ts`, used by `ask-vet-assistant` and `generate-vet-report`) apply this same rule, and a parity test (`src/lib/weightServerParity.test.js`) pins them together.

Access is `observations`' existing rules (0014, 0045, 0057): owners and co-owners read and write weight, and sitters can read weight during an open sit. Weight never affects the Vibe or the symptom count (spec 0012), and there is no weight score or label.

8. AI Integration

**Since spec 0080 (2026-11-24) the app never builds AI context.** It sends `ask-vet-assistant` a task name and ids only; the server writes every instruction (`supabase/functions/ask-vet-assistant/prompts.ts`) and loads the data itself with the caller's own access (`context.ts`), so RLS decides what the AI is told. `src/components/PetAIInsights.jsx` (task `pet_insights`, button-triggered, not cached) now gets: the last 30 days of `daily_check_ins` + `observations` (each day's Vibe and the symptoms logged, kept as two separate signals per spec 0012), active `medications`, the `pet_onboarding` baseline, and weight from `observations` (one weight per day, §7, read through `_shared/weight.ts`). Fewer than 2 non-skipped check-ins → the server answers `{not_enough_data: true}` without calling the AI and the card shows approved wording C. Nothing persists a generated insight; there is no `ai_insights` table. `wellness_scores` was dropped in migration 0061 (the Vet Report's Wellness Overview is built from the same 30 days of check-ins, `generate-vet-report/wellness.ts`).

As of spec `0041`, every AI call site also runs through a shared guardrail layer (`src/lib/aiGuardrails.js`) before/around the actual API call: an emergency-keyword check can block a chat message from ever reaching the AI, and a structured `urgent` flag in the AI's own response can cause its answer to be discarded and replaced with a fixed "contact your vet" redirect. This applies to `PetAIChat.jsx` and `GeneralAskWyskerChat.jsx` (which take free-text questions) and, for the `urgent` backstop only, `PetAIInsights.jsx` (which does not take free text, so the keyword check doesn't apply there).

A second on-demand AI call now exists: `getInsightSummary()` in `src/lib/checkin/trendsClient.js` (backing the Trends screen's Overview sub-tab, `InsightSummaryCard.jsx`), task `trends_summary`. Since spec 0080 the app sends only the pet id and the selected range; the server rebuilds the inputs from the person's check-ins (caller's saved time zone, UTC if none) — still only four values: Appetite, Water Intake, Energy, and Weight. It is not given the Vibe status, the `symptom_count`, or any of the other eight Health/Wellbeing attributes (Bathroom, Stool, Vomiting, Nausea, Mobility, Breathing, Itching, Behavior) — none of those reach the prompt. It requires at least 2 non-skipped check-ins in the last 10 days before calling the AI at all; below that threshold it returns `null` and the Insight Summary card simply doesn't render — there is no explicit "Complete more check-ins to unlock AI insights" message shown, contrary to what this document previously implied. Like `PetAIInsights`, nothing here is persisted — still no `ai_insights` table.

Summary

The data model is relational and owner-scoped via a single shared RLS helper (`is_pet_owner()`, now correctly linking co-owners since migration 0016). Logging has converged on `observations`, weight included (§7); `symptom_logs`, `wellness_scores` and `food_logs` were dropped in migration 0061. `pet_baselines` remains unpopulated, and `pet_onboarding`'s fixed-form baseline is still the only baseline data actually in use. The current per-day health signal is `daily_check_ins.status` (subjective Vibe) plus `daily_check_ins.symptom_count` (objective, unweighted) — the two never combine into a score, and neither is compared against a baseline. Any new feature that reads or writes weight goes through `src/lib/weightClient.js` (or `_shared/weight.ts` on the server), the only way to do so outside the check-in save path. That path (`src/lib/checkin/checkinClient.js`'s `loadCheckInWeightRows` and `removeStandaloneWeights`) reads, re-sends and removes weight rows itself: it keeps the day's weight on re-save and replaces a standalone weight when the owner types or clears one. New features should not assume `pet_baselines` is populated.
