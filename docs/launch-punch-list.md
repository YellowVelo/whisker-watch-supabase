## P0 — Data safety & process (fix regardless of launch timing)

These aren't store requirements, but shipping to real users without them is
reckless — one already caused a real incident.

- [x] **No database backups / PITR configured — resolved.** Confirmed Supabase Daily Backups (free on Pro, 7-day retention) are active. PITR evaluated and deliberately deferred (`$100/mo` add-on, not justified pre-launch — revisit post-launch). Added a nightly encrypted `pg_dump` export to Cloudflare R2, independent of the Supabase account, with 30-day retention — covers project/account-level loss that Daily Backups alone wouldn't. Restore verified end-to-end against a scratch project (schema rebuilt from migrations, real data confirmed in Table Editor). See [requirements-database-backups.md](features/requirements-database-backups.md) for the full design, restore runbook, and known limitations. **Storage bucket files (photos/documents) — also resolved, spec `0049`.** Nightly sync to a dedicated R2 bucket, verified live 2026-08-09.
- [x] **No branch protection / CI gate on `main` — resolved.** `.github/workflows/ci.yml` runs lint + vitest + build (`frontend` job) and the Edge Function integration tests (`edge-functions` job, see item below) on every push/PR to `main`. Branch protection on `main` now requires both jobs to pass before merge (Settings → Branches). One real gotcha hit along the way, worth remembering: the branch name pattern field is a literal, case-sensitive match — a rule saved as `Main` or a non-branch string (`WWBP`) silently applies to 0 branches and can fail to save at all ("Rule is invalid") without a clear error pointing at the actual field. **Confirmed 2026-07-25:** this gate applies to PR merges. An account with bypass permission (repo admin) can still push directly to `main` without CI blocking the push — GitHub reports it as a "bypassed rule violation" rather than rejecting it. CI still runs and reports pass/fail after the fact, but doesn't prevent the push. Worth knowing before relying on this as an absolute gate.
- [x] **No dev/staging environment — resolved, and this line item itself was stale.** Three separate Supabase projects already exist (`Whisker-Watch` prod, `wysker-watch-dev`, `wysker-watch-staging`) and local `.env` already points at `wysker-watch-dev`, not prod — confirmed via `supabase projects list`/`api-keys` and the project's own `.env.example`. The "shared project" risk this item described was no longer true; CLAUDE.md and `0006 Technical Standards.md` both said otherwise and have been corrected.
- [x] **No automated test coverage on the destructive Edge Functions — resolved.** 8 Deno integration tests (`supabase/functions/delete-pet/index.test.ts`, `supabase/functions/delete-account/index.test.ts`) run against real `wysker-watch-dev` data over HTTP — sole-owner delete, co-owner transfer, co-owner leave, and no-access-403 for both functions. Also added a guard to `delete-account` refusing (403) for `account_type in ('test','demo')`, protecting the shared `test1@`/`test2@`/`demo1@` identities from ever being deleted outright (mirroring `reset-sandbox-account`'s existing "never touches the login row" guarantee) — verified live against `test2@wyskerwatch.com`.
- [x] **CI was broken on `main` for several days without blocking pushes — resolved 2026-08-01.** Two independent regressions: (1) `.env.test` (dummy Supabase env vars needed for `vitest`) was accidentally deleted 2026-07-31 while cleaning up `.gitignore` for the new Playwright suite, breaking the `frontend` job; restored. (2) The `resend-webhook` suite's one suppression-round-trip test needs a legacy-JWT-format service_role credential that the newer opaque `sb_secret_...` key can't provide — a `DEV_LEGACY_JWT_SECRET` GitHub secret was added, but was twice populated with the wrong value (the project's JWT *signing secret* rather than the actual service_role JWT) before being corrected. Both jobs are green on `main` as of commit `2091605`. Underscores the existing gotcha above: none of this blocked pushes to `main` the whole time it was broken.


## PWA — install & offline experience (separate from App Store; ships today, no native shell needed)

Full spec: `docs/features/PWA Feature.md`.

**Resolved since the last version of this list:**
- [x] **Chrome "Install App" button can miss the install prompt — resolved 2026-08-01.** Root cause was worse than originally described: `useInstallPrompt()` was only invoked from `src/pages/Settings.jsx`, which sits inside `App.jsx`'s `<Routes key={location.pathname}>` — a tree that fully unmounts/remounts on every navigation. Since the browser's `beforeinstallprompt` event fires once, asynchronously, and can only be caught by a listener already attached at that moment, the offer was silently lost almost every session unless the user happened to already be on Settings when it fired. Fixed per [0032_PWA_Install_Prompt_Global_Capture_Specification_v1.md](features/0032_PWA_Install_Prompt_Global_Capture_Specification_v1.md): the hook is now `InstallPromptContext.jsx`'s `InstallPromptProvider`, mounted in `App.jsx` outside the remounting route tree (same pattern already proven by `AskWyskerContext.jsx`), so the listener attaches once at app load regardless of which screen is showing. `Settings.jsx` consumes it via context instead of calling the hook directly; UI, copy, and analytics events are unchanged.
- [x] **Firefox and non-Safari iOS browsers (Chrome iOS, Firefox iOS) get no install nudge of any kind — resolved as a product decision, 2026-08-01.** Investigated further while scoping the fix above: Firefox desktop has no PWA install option to point users toward at all (removed from the browser years ago), and Firefox Android's install path lives in a different menu than iOS Safari's Share-sheet flow — a single generic fallback banner can't accurately cover both, and would be actively wrong for Firefox desktop. Desktop Safari (macOS) was found to have the same underlying gap (`IosInstallBanner`'s detection requires an iOS device, so it never shows on Mac) but is separately accepted as negligible traffic. Decision: accept the gap for launch across all of the above — no fallback banner built. Revisit only if analytics later show meaningful traffic from these browsers. iOS Safari itself (mobile) is unaffected and already works correctly — confirmed its detection is synchronous (UA/standalone/dismissal checked on mount) rather than an async event, so it never had the same failure mode as the Chrome path.
- [x] `manifest.json` "missing" — was true before `vite-plugin-pwa` was added; the plugin now generates and injects it at build time. Not a static file in `public/`, by design.

## P2 — Security / trust issues

Could cause real harm (spam, data leakage, silent failures, or misleading
launch metrics) to real users post-launch.

- [ ] **`ask-vet-assistant` Edge Function has no rate limiting or abuse protection — found 2026-08-02 while scoping spec `0041`'s AI guardrails.** The function only checks that the caller is a logged-in Supabase user; beyond that, any authenticated account (test, demo, or real) can call it as many times as they want, as fast as they want. Each call is a real, billed Anthropic API request, so this is a cost/abuse exposure, not a pet-safety one — deliberately kept separate from spec `0041`'s emergency-detection work, which is about what happens *within* a request, not how often requests can be made. Needs a fix (likely a simple per-user/per-time-window cap enforced in the Edge Function itself) before or shortly after launch. See [0041_AskWysker_AI_Guardrails_And_Screen_Context_Specification_v1.md](features/0041_AskWysker_AI_Guardrails_And_Screen_Context_Specification_v1.md)'s Repo Findings & Risks section for the full context.
- [ ] **Branded transactional email (signup confirmation, at minimum) lands in spam on at least Yahoo Mail — investigated 2026-07-26, monitoring plan in place.** Confirmed via real signup test: Resend's own delivery webhook shows `delivered_at` populated (the receiving MTA accepted the message), but it arrived in Junk/Spam, not the inbox. **Investigation ruled out the original guess:** SPF, DKIM, and DMARC are all correctly configured (verified via live DNS lookups) and email content is clean — this is not an authentication misconfiguration. Most likely cause: `wyskerwatch.com` is a brand-new sending domain with no track record yet, which mail providers weight heavily regardless of correct setup. See [0022_Transactional_Email_Deliverability_Warmup_Specification_v1.md](features/0022_Transactional_Email_Deliverability_Warmup_Specification_v1.md) for the monitoring/warm-up plan: once 50 real (non-test/demo) confirmation emails have sent cleanly (no bounces/complaints), DMARC moves from monitor-only (`p=none`) to enforcing (`p=quarantine`). Not closeable until that checkpoint is reached.
**Resolved since the last version of this list:**
- [x] **A co-owner's Daily Check-In save could silently overwrite the other co-owner's save for the same day, with no warning to either person — resolved 2026-08-03, spec `0043`.** If Co-Owner A loaded a pet's check-in before Co-Owner B saved a newer entry for that same day, A's subsequent save completely replaced B's with no indication anyone else was ever involved — real, silent data loss between two real people, distinct from the (already-handled) case of one person editing their own earlier entry. Fixed via migration `0046`: `save_daily_check_ins` now optionally checks the existing `daily_check_ins.updated_at` timestamp against what the caller loaded, refuses the save on a mismatch, and hands back what's currently saved instead of overwriting it; `DailyCheckInSheet.jsx` shows a "Someone already saved this day" pop-up ("Keep Mine" / "Keep Theirs") when that happens. Scoped to co-owners only (pet sitters are a deliberate non-goal, left for a possible future spec); does not reopen spec 0026's separate, already-decided "no warning for a solo same-day re-edit" behavior; bulk Catch-Up saves are unchanged (last-write-wins, as before), also by deliberate scope. Verified against real `wysker-watch-dev` data (5 scripted RPC scenarios) and a live two-tab browser reproduction of an actual co-owner race. Deployed to dev, staging, and production. See [0043_Concurrent_CheckIn_Edit_Conflict_Detection_Specification_v1.md](features/0043_Concurrent_CheckIn_Edit_Conflict_Detection_Specification_v1.md).
- [x] **Analytics rollup no longer blends in `test`-account traffic — resolved 2026-08-01.** `compute_daily_analytics_summary()` now excludes `test`-classified accounts from every metric (DAU, check-ins started/completed/skipped); `demo`, `owner`, and `production` activity remain blended together, per product decision — `demo`/`owner` usage is still considered worth counting, only synthetic QA (`test`) traffic is excluded. All existing `analytics_daily_summary` rows were backfilled with the corrected logic. Also fixed in the same migration: `checkins_completed` was undercounting due to querying retired event names (see the `documentation-review-punch-list-2026-07-18.md` P3 item). See [0030_Analytics_Test_Account_Filter_Specification_v1.md](features/0030_Analytics_Test_Account_Filter_Specification_v1.md).
- [x] **Demo Account Phase 3 has no read-only enforcement — resolved differently than originally scoped, 2026-07-31.** The original read-only approach (block every write, [0018_Demo_Account_ReadOnly_Enforcement_Specification_v1.md](features/0018_Demo_Account_ReadOnly_Enforcement_Specification_v1.md)) was implemented, deployed, and reverted the same day (2026-07-26) after unresolved confusion verifying the frontend messaging behavior. On reflection the owner decided outright blocking was the wrong model — demo accounts should feel fully real and writable during a visit. [0027_Demo_Account_Auto_Reset_On_Login_Specification_v1.md](features/0027_Demo_Account_Auto_Reset_On_Login_Specification_v1.md) ships the actual fix instead: every demo login automatically wipes and reseeds the account back to the standard Maple/Cooper baseline first (no exception for the demo admin), and only one demo session can be active at a time. Inviting a co-owner or pet sitter is the one action still blocked outright, since a sent email can't be undone by a reset. Deployed to dev, staging, and prod; verified live end-to-end.
- [x] **Signup confirmation email isn't branded — resolved 2026-07-26, verified end-to-end on prod.** `sign-up`/`confirm-email` Edge Functions built and deployed per [0021_Branded_Signup_Confirmation_Email_Specification_v1.md](features/0021_Branded_Signup_Confirmation_Email_Specification_v1.md). Two real bugs surfaced only by a live signup test (neither caught by code review or the spec's own risk analysis) and fixed the same day: (1) `isSafeEmailUrl()`'s allowed-host default was still `www.wyskerwatch.com` after `APP_URL` was corrected to bare `wyskerwatch.com`, causing the branded email to fail to send — fixed in `_shared/email/utils.ts`. (2) `generateLink({type:'signup'})` turned out to still trigger Supabase's own built-in confirmation email as a side effect (unlike `invite`/`recovery` types) — the user received both Supabase's generic email and the branded one for the same signup. Fixed by switching account creation to `admin.createUser({email_confirm:false})` (no email side effect) followed by a `recovery`-type `generateLink()` call, reusing the same mechanism already proven safe by the existing resend path. All fixes deployed to dev/staging/prod. See the spam-deliverability item above — the branded email itself now sends correctly but isn't reliably reaching the inbox.
- [x] **No bounce/delivery-webhook handling for Resend — resolved 2026-07-26.** `resend-webhook` verifies Resend's signature and updates `email_logs`'s `delivered_at`/`bounced_at`/`complained_at`; a hard bounce or spam complaint also adds the address to a new `email_suppressions` block list, checked by `sendEmail()` before every send. Registered with Resend for production only — dev/staging share one Resend account with prod, so per-environment registration wouldn't meaningfully separate events. See [0020_Resend_Bounce_Delivery_Webhook_Specification_v1.md](features/0020_Resend_Bounce_Delivery_Webhook_Specification_v1.md).
- [x] **`wysker-watch-staging`'s service_role Postgres role may be missing table grants — resolved 2026-07-26.** Confirmed the real cause: every table in staging's database was missing basic select/insert/update/delete grants for every role (anon, authenticated, service_role) — not RLS, not a stale API key, and not scoped to just `profiles`/`daily_check_ins`. Fixed schema-wide via migration 0035, plus `alter default privileges` so any future table inherits the correct grants automatically on every environment. Live on dev, staging, and prod. See [0019_Staging_Missing_Table_Grants_Fix_Specification_v1.md](features/0019_Staging_Missing_Table_Grants_Fix_Specification_v1.md).
- [x] **No DMARC record for `wyskerwatch.com` — resolved 2026-07-25.** Added `_dmarc.wyskerwatch.com` TXT record in Cloudflare: `v=DMARC1; p=none; rua=mailto:dmarc-reports@wyskerwatch.com; pct=100; adkim=r; aspf=r`. Deliberately starts in monitor-only mode (`p=none`) rather than jumping straight to enforcement, since this domain has never had DMARC before — safest to review aggregate reports for a few weeks before tightening to `p=quarantine`/`p=reject`. Confirmed resolving correctly via live DNS lookup. `dmarc-reports@wyskerwatch.com` alias created in Google Workspace to receive reports.
- [x] **Test/demo account email suppression isn't centralized — resolved 2026-07-24, deployed 2026-07-25.** Moved the `account_type` check out of `invite-co-owner/index.ts` and `invite-sitter/index.ts` and into the shared `sendEmail()` itself (via an optional `sentByUserId` param) — any future caller gets the guard automatically instead of needing to remember to add it. Suppressed sends now also leave a `'suppressed'` row in `email_logs` (migration `0032`) instead of no trace at all. Live on dev, staging, and prod; verified live on dev and prod. See [requirements-centralized-email-suppression.md](features/requirements-centralized-email-suppression.md), including a deploy note about pre-existing migration-history gaps found along the way (unrelated to this change) and a follow-up flagged separately for a staging service-role grants issue.
- [x] **Sitter invite emails never actually send — resolved 2026-07-24.** `InviteSitterDialog.jsx` now calls a new `invite-sitter` Edge Function (mirroring `invite-co-owner`), with the same test/demo suppression. Testing this end to end also surfaced three more pre-existing bugs that had silently blocked the sitter-access feature entirely (not just the missing email) — `pet_sitter_access` was missing a `created_by` column every insert needs, and RLS never granted a sitter read access to `pet_sits` or `pets`. All fixed together (migrations 0028–0031) and verified live on dev, staging, and prod. See `docs/features/requirements-sitter-invite-email.md`.

## P4 — Known bugs / UX gaps

- [x] **Adding a pet from Home is a double hop — working as designed, closed 2026-08-01.** Home's "Add Pet" link (empty state only) navigates to `/pets` rather than opening `AddPetDialog` directly. Confirmed with Lynn this is intentional IA, not a bug: Home is the household-level view, Pets is where individual pets are managed and added. No fix needed.
- [x] **Shared/co-owned (sitter-access) pets show no Wellbeing chips — resolved 2026-08-02, spec `0037`.** The component this item originally named, `SharedPetRow`, no longer exists under that name — it's `SitterPetRow` now (`src/pages/Pets.jsx`) — and it really was just a bare identity link (photo + name only) with no chip UI of any kind. Turned out to be a two-part gap, not just a missing component: the database's row-level security only ever let a pet's owner/co-owner read `daily_check_ins`/`observations` (the tables Wellbeing-chip data comes from), so a sitter was blocked from that data even after the UI existed. Fixed both: migration `0045_daily_check_ins_observations_select_sitter.sql` adds sitter-read policies on both tables (deployed to `wysker-watch-dev`, `wysker-watch-staging`, and `Whisker-Watch` prod), and `SitterPetRow` now shows the same 5 Wellbeing chips an owner sees — but read-only (not tappable), since the whole row is already a single tap target to Trends and a clickable chip nested inside it would be invalid markup. Chip-loading/rendering logic extracted into a new shared `WellbeingChipGrid.jsx` component so the owner's card and the sitter's row don't carry two drifting copies. Verified live end-to-end on `wysker-watch-dev`: signed in as `test1@wyskerwatch.com` (owner) and `test2@wyskerwatch.com` (sitter) in the same session, confirmed the sitter's chips showed "No check-in yet" before a check-in existed and real "versus yesterday" data immediately after one was logged. See `docs/features/0037_Sitter_Wellbeing_Chips_Specification_v1.md`.
- [x] **Pets-tab's Wellbeing chips navigate to Trends instead of launching Daily Check-In — working as designed, closed 2026-08-01.** Confirmed with Lynn: routing the chip to Trends is the intended behavior, not a missing check-in shortcut. `PetProfileContent.jsx`'s `context === 'pets'` chip block (`~line 481`) renders `AttributeTrendChip` with `onClick` routing to `/pet/:id/trends?...` — no fix needed.
- [x] **`TermsOfServiceSection.jsx` and `PrivacyPolicySection.jsx` duplicate rendering logic — resolved 2026-08-02, spec `0038`.** `BodyLink`/`BodyBlock` extracted into a new shared `src/components/legalContentBlocks.jsx`, imported by both page components instead of each defining its own copy. The section-lookup function (`getTermsOfServiceSection`/`getPrivacyPolicySection`) was also unified into a new shared `getLegalSection` helper in `src/lib/legalContent.js`, since both content files had the exact same lookup logic. See `docs/features/0038_Legal_Section_Rendering_Deduplication_Specification_v1.md`.
- [x] **Home screen's tap-target audit and loadData() race guard — resolved 2026-08-02, spec `0039`.** The audit confirmed most of Home was already compliant, but found two real issues: the "Catch up yesterday"/"Catch up now" banner buttons had no minimum tap-target size, and the pet card's outer `<Link>` contained nested `<button>` chips — a button inside a link, which is invalid HTML and can confuse screen readers even though it worked visually. Fixed both: the Catch Up buttons now meet the 44px floor, and `PetSummaryCard`'s outer element was changed from `<Link>` to an accessible `<div role="link">` with manual click/keyboard handling, so the chips are no longer nested inside another clickable element. `loadData()` now guards against overlapping reloads (initial load, the auto-detected→profile timezone swap, pull-to-refresh, Retry) with a request-generation counter, so a slower, earlier reload can no longer overwrite state from a newer one. Verified with the full Playwright suite (23/23 passing, including a new keyboard-navigation test) and manual in-browser checks. See `docs/features/0039_Home_TapTarget_Audit_And_LoadData_Race_Guard_Specification_v1.md`.
- [x] **On desktop-width screens, an invisible toast-notification container can block clicks on the bottom tab bar's "Menu" tab — resolved 2026-08-01, spec `0033`.** Found 2026-08-01 while writing a Playwright test for spec `0032` (the PWA install-prompt fix) — `page.getByRole('link', { name: 'Menu' }).click()` failed after 30+ retries with Playwright reporting a specific element intercepting the click. Root cause: `Toaster`'s `ToastViewport` (`src/components/ui/toast.jsx:15-21`, shadcn/ui's default toast-notification positioning) is styled `fixed ... sm:bottom-0 sm:right-0 md:max-w-[420px]` — at `sm:` viewport widths (640px) and above, this is the same bottom-right corner where `BottomTabBar.jsx`'s rightmost tab ("Menu," which routes to Settings) sits. Even with zero active toasts, the container's `p-4` padding creates a real, clickable (if invisible) box in that corner, and it sits at `z-[100]` — above the tab bar. This means a real Chrome/Edge **desktop** user (exactly who the Settings "Install App" row targets) could have clicks on the Menu tab silently swallowed, depending on exact layout/viewport width. Never caught before because no existing e2e test clicked that tab (`login.spec.js` only checks it's visible, never interacts with it).
